# 設計 06: 深掘り体験(フェーズ2 B)

ステータス: v1(2026-07-19)/ 上位文書: [../PROPOSAL.md](../PROPOSAL.md) §フェーズ2境界(齟齬時は PROPOSAL が優先)・ADR 0002/0003/0004 / 対象読者: 実装者(本人)

## 0. 位置づけと決定方法

- ADR 0004(深掘りは既存エージェント内・知見の substrate は Obsidian)の体験を具体化する設計。知見 = 深掘りの副産物(ADR 0003)、retrieval 北極星(ADR 0002)を前提とする。
- 決定方法: 体験を先に設計し、**疑似体験デモ 2 周(2026-07-19)**で検証してから本書に確定した。デモ実物は vault の `SignalForge/DeepDive/` にある 20260719-3664(日本語 gist・観点指定あり)/ 20260719-3673(英語記事・自動選出)の 5 ノート。フォーマットの正はデモ実物。
- PROPOSAL 進出条件との関係: PROPOSAL §フェーズ2境界の **2026-07-19 改訂**(同時 PR)を参照。件数条件は超過、「50% 手動深掘り」は測定意味を失い、「関連リンク収集のみ」軽量段の検証は疑似体験デモ 2 周で代替して、ユーザー判断でフル調査段の実装へ進む。安全条件は変更なく継承する。

## 1. 体験の全体像

**分業型 3 フェーズ**。従来の「デスクでまとまった時間を確保して対話的に読む」は成立しにくい(それが深掘りできない原因)ため、調査と理解を分離する。

| フェーズ | 主体 | 場所・時間 |
|---|---|---|
| 調査 | AI(朝バッチ) | 非同期・夜間〜朝 |
| 理解 + take | 本人 | スマホ・すきま時間(お風呂含む) |
| 対話(継続深掘り) | 本人 + agent | デスク・必要時のみ |

- リズムは **夜選ぶ → 朝届く**。即時実行はしない(即時性の要求はユーザー確認済みで無し)。
- **段階的深度ラダー**: 概要カード(30 秒)→ 解説ノート(5〜10 分)→ 対訳/原文(任意)→ take 一言。各段で降りてよく、深く読まない選択は正当(デモ 2 周目で「解説まで読んで対訳に行かない」が自然に成立することを実証)。全部読む義務を作らない。

## 2. 夜の入口(選択とパス)

- 材料は 21:30 の未消化一覧(番号付き。GH#99 でブックマークが合流済み)。
- **自由文リプライ**で指定する: 「3664 を◯◯の観点で」「3773 はパス」。番号 + 観点(interest angle)/ パスを抽出する。スマホの音声入力による話し言葉を許容する(厳密な書式を要求しない)。パーサは**規則ベースで確定**(GH#104 の実装決定): 候補に実在する番号だけを命令の区切りにし(本文中の「GPT-5」等を誤検出しない)、番号直後がパス語だけなら除外、それ以外は残り全文が観点として調査段へそのまま渡る。構文は番号とパス語だけなので LLM は不要(poller を軽く保つ)。Telegram ボイスメッセージ(音声ファイル + STT)は拡張であり本設計のスコープ外。
- **観点は調査ブリーフの軸**になる。ユーザーの疑問から掘ることで、非同期でも能動性を部分的に保つ。
- **パス**は深掘りキューからの除外のみを意味する。保存アイテムとしての未消化管理(あとでカジュアルに読む)には影響しない。🔖 には「後で読みたいだけの趣味のもの」が混ざる前提で、パスを一等市民の操作にする。

## 3. キューと量制御

- **新規 🔖 ブックマークは無条件でキュー入り**(ブックマーク行為 = 「後でしっかり見たい」の意思表示)。
- **調査実行は 1 日上限 N 件**(既定 2、config で変更可)。優先順位: ①夜リプライで観点付き指定されたもの ②新着ブックマークの新しい順。
- backfill 済みの既存ブックマーク(GH#100 時点の 117 件)は自動実行の対象外。リプライで指定されたときだけ掘る。
- パス済み・調査済みのアイテムはスキップする。
- 制約の根拠: 実行時間(朝バッチは 06:30 起動・07:15 watchdog。デモ実測で 1 件 5 分弱)と読む側の供給量(1 日に消化できるドラフトは 2〜3 本。未読ドラフトの山は未読負債の再生産であり本末転倒)。

## 4. 朝の調査段(ドラフト生成)

- 朝バッチに深掘り段を追加する。**実行主体(codex app-server / claude headless 等)は実装時に決定**(ADR 0004・memory 参照)。
- 安全条件は PROPOSAL §フェーズ2境界を継承する: read-only 基本・**書き込み先は vault の `SignalForge/DeepDive/` に限定**・送信/投稿/購入等の自動実行アクション禁止・untrusted 本文(取得した記事・gist 等)を起点とする実行はツール制限必須・long polling 維持。
- ブリーフの立て方:
  - **観点指定あり**: 指定された観点への答えを最優先の問いにする。
  - **自動選出(観点なし)**: 自動ブリーフ =「ユーザー文脈との接点を軸に、主張と根拠の強さを検証しながら読む」。ユーザー文脈の材料は当面は既知のプロジェクト文脈、将来は蓄積された知見ノート(知見が溜まるほど個人化される。ADR 0003 と整合)。

## 5. 成果物フォーマット

### 5.1 解説ノート(`kind: deepdive`)

- 置き場所: `SignalForge/DeepDive/`、ファイル名は Items 準拠の `YYYYMMDD-<item_id>-<slug>.md`。
- frontmatter: `id` / `kind` / `title` / `url` / `author` / `published` / `requested`(観点 or 「観点指定なし: 自動キュー」)/ `auto_brief` / `status`(`take待ち` → `take済`。遷移条件は §6)/ `related`。
- 節構成(順序も含めデモで確定):
  1. **概要(2 方面)**: 「あなたにとって」(観点への答えの核心 + 自分の文脈への具体的含意)と「世の中にとって」(なぜ話題か・何が新しいか)。アウトカムベースで書く(キーワード羅列にしない)。
  2. **書き手の立ち位置**: 1 段落。誰が・どの立場・想定読者。主張の深さとスコープを読者が推定するための材料(デモで、立ち位置の推測が外れる実例により有効性を実証)。
  3. **骨子**(記事の論旨)
  4. **根拠の強さ(検証)**: 主張を鵜呑みにせず、数字の質・因果の強さ・利益相反を評価する常設欄。自動選出時ほど重要。
  5. **自分への接続**(signal-forge・自分の執筆・進行中の関心)
  6. **残った問い**(続き深掘りの候補)
  7. **ソース**(原文ノートへの wikilink 含む)
  8. **take 領域**(手書き・追記はリプライ経由でも入る)

### 5.2 原文・対訳ノート(`kind: deepdive-source`)

- **日本語ソース**: 原文保全ノート(全文コピー・私的利用。取得日時と原典 URL を frontmatter に記録)。
- **英語ソース**: 対訳ノート — **日本語全訳を地の文にし、英語原文は節ごとの折りたたみ callout(`> [!quote]-`)に格納**。スマホでは日本語をすらすら読み、確認したい箇所だけ原文を開く。段落交互(EN/JA)はスクロール長が倍になるため採らない。
- 原文を別ノートに分けるのは解説ノートの読み心地を守るため(デモ 1 周目の設計発見)。
- **X 本文非保持ポリシー(GH#2)の例外条件**: ツイート原文全文の恒久保存は行わない。Web 記事・gist は私的利用の範囲で全文保全・対訳可。ライセンス上の注意があれば frontmatter に記す。

### 5.3 Telegram 概要カード(1 通・分割しない)

構成(v3。デモ 2 周のフィードバックで確定):

```
🔎 深掘り #<item_id>「<日本語訳タイトル>」(<原題・原語のとき>)
✍️ 書き手: <立ち位置 1 行>
<選出ラベル: 観点「…」 or 🤖 自動選出(🔖新着)・観点なし>

あなたにとって
<アウトカムベース 3〜5 行>

世の中にとって
<3〜4 行>

📄 ノート: SignalForge/DeepDive/<file>(対訳ありの場合はその旨)
💬 リプライが take として記録されます
```

- タイトルは必ず日本語(英語原題は括弧で併記)。`analyses.title_ja` があれば再利用。
- 「あなたにとって / 世の中にとって」の 2 方面は読む・読まない判断の材料。「世の中的に大事だが自分には遠い」の未読を正当化できる。

## 6. take と接続

- カードへのリプライは GH#96 の感想リプライ基盤が受け、LLM パースで **take(結論・感想・評価)** と **続き要求(質問・追加の観点)** に分類する。一つのリプライに両方が含まれてよい(デモ 1 周目のリプライは「判定軸に興味を持った(take)+ そこを読み込みたい(続き要求)」の複合だった)。
  - **take** → ノートの take 領域へ追記 + `followup_dig` に記録(GH#99 の既知境界「ブックマークの消化動線」をここで閉じる)+ ノート status を `take済` へ。
  - **続き要求** → **続きの観点**として登録(即その場で対話するか、翌朝のキューに観点付きで積む)。status は遷移しない(`take待ち` のまま。続き要求は結論ではないため)。
- ノートの status 遷移: `take待ち` →(take 記録時のみ)→ `take済`。**知見として確定した扱いになるのは take が付いた部分だけ**であり、take のないドラフトは AI ドラフトのまま(ADR 0003 の「AI ドラフト + ユーザー take だけ確定」と整合。retrieval 側はこの status で確定/未確定を判別できる)。
- デスクでの対話(継続深掘り)の成果は、解説ノートに**続章として還流**する(知見 = 深掘りの副産物。ADR 0003)。
- **KPI 非接続原則**: take の記録を KPI・ランキングへ自動接続しない(2026-07-18 の判断と同根。測定定義を汚さない)。

## 7. 実装分割

レビュー可能な単位で 3 分割(段階導入の位置づけは PROPOSAL §フェーズ2境界 2026-07-19 改訂を参照。軽量段の検証はデモで代替済みのため、①は入口のみ・②でフル調査段を実装する):

1. **夜の入口**: 深掘りキュー(スキーマ)+ 自由文リプライのパース(番号 + 観点 / パス)+ 未消化一覧との接続
2. **朝の調査段**: 上限 N 件の実行制御 + ドラフト生成 + DeepDive ノート出力 + 概要カード配信
3. **take 記録**: カードリプライ → take 領域追記 + followup_dig 記録 + 続き観点の登録

運用前提(コード外・ユーザー作業): Obsidian vault のモバイル同期(iCloud 等)。未設定でもフェーズ①②の価値は毀損しない(PC で読める)。
