# 設計 06: 深掘り体験(フェーズ2 B)

ステータス: v1(2026-07-19)。2026-10-31 に GH#349 で候補の選び方と状態の見せ方を改訂(実装は §7 の順で進める)/ 上位文書: [../PROPOSAL.md](../PROPOSAL.md) §フェーズ2境界(齟齬時は PROPOSAL が優先)・ADR 0002〜0005 / 対象読者: 実装者(本人)

## 0. 位置づけと決定方法

- ADR 0004(深掘りは既存エージェント内・知見の substrate は Obsidian)の体験を具体化する設計。知見 = 深掘りの副産物(ADR 0003)、retrieval 北極星(ADR 0002)を前提とする。
- 操作面は ADR 0005(2026-10-18): 機能は signal-forge が口として持ち、操作するアプリは別プロジェクトの中央アプリで作る。当面の操作面は Telegram で、カードへの質問にもその場で答える(GH#126)。
- 決定方法: 体験を先に設計し、**疑似体験デモ 2 周(2026-07-19)**で検証してから本書に確定した。デモ実物は vault の `SignalForge/DeepDive/` にある 20260719-3664(日本語 gist・観点指定あり)/ 20260719-3673(英語記事・自動選出)の 5 ノート。フォーマットの正はデモ実物。
- PROPOSAL 進出条件との関係: PROPOSAL §フェーズ2境界の **2026-07-19 改訂**(同時 PR)を参照。件数条件は超過、「50% 手動深掘り」は測定意味を失い、「関連リンク収集のみ」軽量段の検証は疑似体験デモ 2 周で代替して、ユーザー判断でフル調査段の実装へ進む。安全条件は変更なく継承する。

## 1. 体験の全体像

**分業型 3 フェーズ**。従来の「デスクでまとまった時間を確保して対話的に読む」は成立しにくい(それが深掘りできない原因)ため、調査と理解を分離する。

| フェーズ | 主体 | 場所・時間 |
|---|---|---|
| 調査 | AI(朝バッチ) | 非同期・夜間〜朝 |
| 理解 + take | 本人 | スマホ・すきま時間(お風呂含む) |
| 対話(継続深掘り) | 本人 + agent | カードへの質問は Telegram でその場で返事(GH#126)/ 腰を据えた対話はデスク・必要時のみ |

- スマホでの理解は、当面は概要カードと質問への返事(Telegram)で行い、ノート全体は PC で読む。スマホでノート全体を読む面は中央アプリ(別プロジェクト)で解く(ADR 0005)。

- リズムは **夜選ぶ → 朝届く**。即時実行はしない(即時性の要求はユーザー確認済みで無し)。
- **段階的深度ラダー**: 概要カード(30 秒)→ 解説ノート(5〜10 分)→ 対訳/原文(任意)→ take 一言。各段で降りてよく、深く読まない選択は正当(デモ 2 周目で「解説まで読んで対訳に行かない」が自然に成立することを実証)。全部読む義務を作らない。

## 2. 夜の入口(選択とパス)

- 材料は 21:30 の未消化一覧(番号付き。GH#99 でブックマークが合流済み)。
- **自由文リプライ**で指定する: 「3664 を◯◯の観点で」「3773 はパス」。番号 + 観点(interest angle)/ パスを抽出する。スマホの音声入力による話し言葉を許容する(厳密な書式を要求しない)。パーサは**規則ベースで確定**(GH#104 の実装決定): 候補に実在する番号だけを命令の区切りにし(本文中の「GPT-5」等を誤検出しない)、番号直後がパス語だけなら除外、それ以外は残り全文が観点として調査段へそのまま渡る。ただし次の番号の前置き(「。それと」「、あと」)は前の命令に混ぜない。切るのは命令どうしの区切りと分かるところだけで、最後の句点・改行より後ろと、読点の後ろが接続語(「あと」「それと」など)だけの部分を切る。パス語の直後に読点があれば、そこで命令を終える。読点の後ろに自由文が続くときは観点の一部として残す(「3664 をコスト、運用の観点で 3773 はパス」の観点は「コスト、運用の観点で」。GH#238)。構文は番号とパス語だけなので LLM は不要(poller を軽く保つ)。観点を書かずに指定し直したとき(「3664 も」)は前回の観点を引き継ぎ、受け付けの返信には番号ごとに実際に使う観点を出す(引き継いだときはその旨も。観点は設計 04 §1 の規定で escape し、表示だけ 300 字で切る。1 通に収まらなければ行の単位で複数通に分ける。GH#194・GH#228)。Telegram ボイスメッセージ(音声ファイル + STT)は拡張であり本設計のスコープ外。
- **観点は調査ブリーフの軸**になる。ユーザーの疑問から掘ることで、非同期でも能動性を部分的に保つ。
- **パス**は深掘りキューからの除外のみを意味する。保存アイテムとしての未消化管理(あとでカジュアルに読む)には影響しない。🔖 には「後で読みたいだけの趣味のもの」が混ざる前提で、パスを一等市民の操作にする。
- **一覧の各行の状態(GH#349)**: どれを掘る予定か、掘り終えたか、なぜ掘られないかを本人が確かめる場所は、この未消化一覧に置く(別の一覧や command は足さない)。各行の番号の後に、深掘りの状態を短い印で添える。
  - 🗓 明朝: 明朝に掘る予定(下の「明朝の予定」)。
  - ⏳ 待ち: キューにあり本文もあるが、上限の枠の外(次の朝以降に掘る)。
  - ✅ 掘った: 掘り終えて take 待ち(`dig_queue.status = 'done'`。take を返すと `followup_dig = yes` になり一覧から消える。§6)。
  - ⏭️ パス: パス済み(リプライのパスと下の skip のボタン)。
  - ⚠️ 本文なし: キューで `queued` のまま、またはキューに無い item で、本文が保存の期間を過ぎて消え、掘れない(§3 の材料不足)。
  - 印なし: キューに無い(Telegram の 🔖 ボタンだけの item や backfill の X ブックマーク。§3)。リプライで指定すれば掘る。
  - 判定の細目(実装で決めた): ⚠️ の条件は §3 の材料不足と同じ(`[dig].min_body_chars` に満たない)。本文の抽出に失敗した item も ⚠️ になる。✅ と ⏭️ は本文の有無を問わず、キューの状態で示す。
  - `[dig].daily_cap = 0`(深掘りの段が止まっている)のときは、印も予定も skip のボタンも出さず、今の一覧のままにする。
- **明朝の予定(GH#349)**: 夜の一覧を作る時点のキュー(§3 の ①②)を、朝の選定と同じ規則(同じ関数を共用する)で並べ、翌日の上限の件数ぶんを「明朝」とする。予定の行は一覧の先頭に置き、一覧の上限(15 件。設計 04 §4)に数えずに必ず載せる。🔖 の一覧に無い予定(カードからの調べ直しの依頼など)も行として足す。🔖 の一覧が空でも予定があれば一覧を送る。
  - 夜の予定は確約ではない。朝までに次で変わりうる。夜の後のリプライと skip(本人の操作)、カードへの調べ直しの依頼(①)、朝バッチの x_signals 段が取り込む新しい 🔖(② は新しい順なので、夜の予定の ② を押し出しうる)。本文は消えない(purge は dig 段の後。設計 00 §2)。そこで夜は「キューからの予定」とだけ示し、一覧に「朝に新しい 🔖 が入ると入れ替わることがあります」と 1 行添える。押し出された候補はキューに残り、次の朝以降に掘る(押し出しを知らせるかは §8 の未決)。
  - §3 の ③(digest の上位)は朝の digest で決まるので、夜には示さない。キューの予定が上限に足りないときは「残り N 件は明朝のダイジェストの上位から選びます」と 1 行で示す。朝に実際どこから選んだかは、カードの選出ラベルで分かる(§5.3)。
  - 実装で決めた細目: 選定の規則は `app/dig.py` の `select_from_queue`(①②)に置き、朝の段はその後に ③ を足す。夜は一覧を送る日の JST の翌日を「明朝」とし、件数は `[dig].daily_cap`(夜の時点で翌日の実行数は 0)。予定は読むだけで、キューに書かない。
  - 見出しの件数は、予定の行を含む一覧の全行数にする。「他 N 件」は、予定を除いた残りの行のうち 15 件を超えた分。2 つの注記は行の後に空行を挟んで置き、リプライの案内はその後にする。入れ替わりの注記は「🗓 明朝 = キューからの予定。朝に新しい 🔖 が入ると入れ替わることがあります」で、予定が 1 件以上あるときだけ出す。digest で埋める注記は、予定が 0 件のときも同じ文言(残りの件数 = 上限)にする。
  - 予定の行の番号はキューにあるので、🔖 の一覧に無い行もリプライで指定できる(リプライの候補はキューの item を含む。poller の `queue_item_ids`)。リプライの例の番号は先頭の行にする。
  - 予定の行は上限に数えず、`[dig].daily_cap` にも上限が無いので、一覧が 1 通に収まらない日がありうる。可視の長さ(href の URL を数えない。UTF-16 で数える)が 4000 字を超えるなら、行の単位で複数通に分ける。見出しは 1 通目に、注記とリプライの案内は最後の 1 通に置き、2 通目以降には「🔖 未消化の深掘り候補(続き)」を付ける。どの 1 通も `dig_backlog_messages` に記録し、リプライを受け付ける。
  - 一覧の送信に失敗しても、続く追い掛けは送る。失敗は追い掛けの後に投げ直し、内蔵タイマーの失敗としてログに残す。夜アンケートは送る前に送った印を付けるので、一覧はその日には送り直さない(今までと同じ)。送れた分の 1 通は台帳に残る。
- **skip のボタン(GH#349)**: 「明朝」の行ごとに、一覧のメッセージに「⏭️ {id} を外す」のボタンを付ける(自由文のリプライのパスは今までどおり使える)。押した後の扱いはリプライのパスと同じで、深掘りのキューから外すだけ(`dig_queue.status = 'passed'`。観点と `requested_at` は残し、受付の順序の印も同じく残す。GH#235)。保存アイテムの未消化は変えないので、行は ⏭️ パスの印で一覧に残る。戻すときはリプライで指定し直す(「{id} も」)。
  - callback の認可は設計 04 §6 の allowlist(`from.id`)に従う。さらに、押されたメッセージが未消化一覧(`dig_backlog_messages`)で owner の chat にあることを確かめてから反映する(callback_data だけを信じない。深掘りカードのボタンと同じ。設計 04 §3)。前の夜の一覧のボタンも、リプライと同じく受け付ける。
  - 朝の生成中に押されたときは、リプライのパスと同じく本人の操作を優先する(キューの done 化は選定のときの値との compare-and-set で、生成中のパスを上書きしない。設計 01 §7 末尾。生成物のカードは届く)。

## 3. キューと量制御

- **新規 🔖 ブックマークは無条件でキュー入り**(ブックマーク行為 = 「後でしっかり見たい」の意思表示)。
- **調査実行は 1 日上限 N 件**(既定 2、config で変更可)。優先順位: ①夜リプライで指定されたもの(観点の有無を問わず、指定の新しい順)②自動キュー(新着ブックマーク)の新しい順 ③その日の digest の上位(①②で上限に足りない分だけ。GH#349)。
- **digest の上位から埋める(GH#349。2026-10-28・2026-10-31 決定)**: ①②で選んだ件数が上限に足りない日は、足りない分(上限 − その日の実行数 − ①②の件数)を、その日の digest の上位から選んで掘る。本人の指定と 🔖 を先に掘る順は変えない。キューに掘れる候補が無い日もカードが届き、ふだんの朝は上限の件数(既定 2 件)がほぼ届く。
  - 選び方の既定: その日(JST の暦日)の `digests` 行のうち配信済み(`delivery_status = 'sent'`)のものの `item_ids`(配信順 = ランキングの順)を上から見る。🔖 保存節(`bookmark_item_ids`)は見ない(X のブックマークは ② の経路にある)。次を除いて、足りない件数だけ取る。
    - `dig_queue` に行がある item(状態を問わない。`queued` で ② に選ばれなかったものは本文なし、`passed` はパスと skip、`done` は掘り済み)。
    - `dig_results` に行がある item(掘り済み)。
    - 材料不足(下の「材料不足」と同じ条件)。黙って次の item へ進み、枠を使わない。
  - その日の digest が無い・配信されていない日(障害・`intel dig` を digest の前に走らせたとき)は ③ を選ばない。
  - 記録の既定: 選ぶ時点ではキューに積まず、生成物を台帳に write-ahead するのと同じトランザクションで、`dig_queue` に `source = 'digest'`・`status = 'done'` の行を足す(設計 01 §7 末尾)。行を作るのは、後で同じ item に X のブックマークが付いても自動キューが掘り直さない(自動投入は既存の行を変えない)ため、③ の除外が「キューに行があるか」で済むため、夜の一覧と調べ直しの依頼が他の行と同じ規則で扱えるため。以後はほかの行と同じで、リプライの指定と調べ直しの依頼で `queued` に戻り、`source` は `digest` のまま変えない(初回投入の経路で以後不変)。
  - 生成中にできた行との競合(GH#349): 選んでから記帳するまでの数分の間に、同じ item の行を poller などが作ることがある。生成中に本人がその item に 🔖 を付けて一覧へリプライした(指定・パス)、別の実行の x_signals 段が X のブックマークを取り込んだ、など。記帳は ①② の done 化と同じく本人の操作を優先し、生成物は必ず記帳する。行を足すのは「行が無いときだけ」にし(item_id の UNIQUE に当たって台帳の記帳ごと戻らないようにする)、行があれば次のとおりにする。
    - 本人の明示の操作の行(`requested_at` のある指定と、`passed`)は変えない。指定は次の朝に掘り直し(観点があればその観点で。新しいノートは `previous` で今回につながる。§6)、パスはパスのまま残る。①② の compare-and-set で生成中の再指定・パスを上書きしないのと同じ考え方(設計 01 §7 末尾)。
    - 自動投入の行(`requested_at` が無く `queued`。X のブックマークの取り込み)は `done` にする。本人の明示の操作ではなく、掘ったばかりの item を翌朝にまた掘らないため。`source` は先にできた行の値(`bookmark`)のまま変えない。
    - どの場合も、生成物の公開とカードの送信は行う(①② で状態を保持したときと同じ)。生成に失敗した item は行が無いまま残り、同じ日に再実行すればまた選ばれうる(①②の失敗はキューに残って次の朝に持ち越すが、③ はその日の digest からしか選ばないので、次の朝には持ち越さない。失敗は段の失敗として知らせる)。
  - `source` に `digest` を足すため、migration 009 の CHECK を migration 027 で広げた(SQLite なので表を作り直す。§8 の既定の案)。
  - ブリーフは自動選出と同じ(観点なし。§4)。
- backfill 済みの既存ブックマーク(GH#100 時点の 117 件)は自動実行の対象外。リプライで指定されたときだけ掘る(③ も 🔖 保存節を見ないので選ばない)。
- パス済み・調査済みのアイテムはスキップする。
- **材料不足(GH#197)**: 材料は DB の抽出本文(`documents.extracted_text`)で、`[dig].min_body_chars`(既定 200 字)に満たないアイテムは掘らない。自動選出(② と ③)なら枠を使わずにキューに残す(毎朝の失敗にしない。③ は積まずに飛ばす)。リプライ指定なら段の失敗として 1 回だけ知らせ、指定を外す(`requested_at` を消す。状態・観点・受付の順序の印はそのまま。以後は自動選出の材料不足と同じ扱い)。本文は保存の期間(設計 01 §6。既定で RSS 30 日・X 7 日)を過ぎると purge で消え、取り直す経路を持たないので、指定のままにすると毎朝同じ失敗を知らせ続けるため。本人が指定し直せば、また 1 回知らせる。
  - 外すのは、朝バッチの失敗の通知(設計 05 §4)をその実行で送れた後(GH#337)。dig 段の中では外さず、外す候補を段の失敗と一緒に返す。段の中で外すと、通知までの間(他の件の深掘り・公開・送信で分オーダー)に止まったとき、指定だけが消えて本人に届かない(次の実行は自動キューの材料不足として、知らせずに飛ばしてしまう)。
  - 通知の前に止まったときは指定が残り、次の実行がリプライ指定としてもう一度選んで知らせる。通知を送らなかったとき(今日は通知済み・Telegram が未設定・送信に失敗した)も指定を残し、次の朝の実行が知らせてから外す。`intel dig` は失敗の通知を送らないので外さない(次の朝バッチが知らせて外す)。
  - 送った後、外す前に止まると、次の朝にもう 1 回知らせる(1 回多く知らせても、知らせ漏れは作らない)。外せなかったとき(選定の後に本人が指定し直した・パスした・DB の更新に失敗した)は本人の操作と指定を残す。指定が残っていれば次の朝にもう一度知らせる(compare-and-set。ログに WARNING を残す)。
  - 深掘りカードへの調べ直しは、受け付ける前に同じ条件で確かめる(§6)。
- **本文の消えた item(GH#349)**: 本文の消えた item は、取り直す経路が無いので掘れないまま `queued` で残る。既定では、キューの状態を変えず(自動でパスにしない)、夜の一覧で ⚠️ 本文なしと示す(§2)。予定にならないので skip のボタンは付けない。朝の選定は今までどおり黙って飛ばす。自動でパスにしないのは、パスが本人の明示の操作で、受付の順序の印(GH#235)を伴うため。一覧に残り続けるのは未消化の管理(カジュアルに読む)のためで、キューの状態とは別の話(パスにしても一覧からは消えない)。本文なしの行が一覧の上限を占めるときの扱いは §8 の未決。
- **候補の無い朝の知らせ(GH#349)**: その日の上限に達していないのに、①〜③のどれからも 1 件も選べず、その実行でカードを 1 通も送らなかったときは、dig 段の終わりに Telegram で短い 1 通を送る。新しい候補が 0 件でも、前の実行で中断した分(未公開のノート・未送信のカード。§4・設計 01 §7 末尾)を台帳から再開してカードが届く朝があり、そのカードの直後に「深掘りはありません」と知らせないため。カードが届かない理由を本人が分かるようにするため(改訂の前は、キューに本文の残った候補が無い朝に、カードも知らせも届かなかった)。
  - 文面は固定の文言だけにし、外部由来の本文を入れない。理由は 2 通りに分ける。「🔎 今朝の深掘りはありません。キューにも今日のダイジェストにも、掘れる候補がありませんでした」と「🔎 今朝の深掘りはありません。今日のダイジェストが配信されていないため、上位から選べませんでした」。どちらも理由の後に句点と改行を置き、「今夜の未消化一覧へのリプライで指定できます」を添える。digest を配信したかは、③ と同じく、その日の `digests` 行が `delivery_status = 'sent'` かで見る。
  - 失敗の通知(設計 05 §4)とは別の知らせで、段の失敗にしない。リプライの指定が材料不足で掘れず、ほかに 1 件も選べなかった朝は、失敗の通知とこの知らせの両方が届く(この知らせを先に送る)。知らせを送れなかったとき(Telegram・DB の失敗)はログに ERROR を残すだけで、段の結果を変えない。
  - 送らないとき: 上限に達していて選ばなかった朝、新しい候補は無いが中断した分のカードを再開した実行(送れなかったときも送らない。失敗の通知で知らせ、次の実行が送る)、選べたが生成に失敗した朝(失敗の通知に任せる)、別の実行が調査段を進めていて何もしなかった実行(下の「実行は 1 つずつ」)、Telegram が未設定のとき、`daily_cap = 0`(段ごと省く)。同じ日に 2 回目以降の実行(`intel run` の再走・`intel dig`)では送らない。
  - 同じ日に 2 回送らない印(GH#349 で決定): `telegram_state` の日付キー `dig_no_candidate_notified_date` に、送れた日(JST の暦日)を記録する。migration は足さない。印は送れてから記録する(失敗の通知と同じ)。送れなかった日や、送る前に止まった日は、同じ日の次の実行が知らせ直せる。これとは別に、その日に先の実行がカードを送っていれば(台帳の `sent_at` が今日)送らない。先の実行が上限の一部だけを掘った日の再走で、届いたカードと食い違う「深掘りはありません」を出さないため。印を「その日に実行した」の意味にしなかったのは、知らせを送る前に止まった実行や、送れなかった実行の後に、知らせが届かないままになるため。
- **実行は 1 つずつ(GH#196)**: 朝バッチの dig 段と `intel dig`(手動の `intel run` の dig 段も)は同じ台帳を使う。候補の選定から公開・送信までを、DB の隣の `<DB>.dig.lock`(既定 `intel.db.dig.lock`。flock。migrate.lock・deliver.lock と同じ名付け。設計 01 §10・04 §2)で 1 つに絞る。重なると、両方が同じ候補を選んでそれぞれ生成し、1 日上限を超え、カードが重複する。保存されるノートは先の生成物(既存のノートは置き換えない。§4)なので、後のカードとノートの生成元も食い違う。
  - 後から来た実行は待たずに何もしないで終える。朝バッチでは dig 段を失敗にせず、WARNING を残して purge・backup へ進む。`intel dig` は理由を表示して終了コード 0 で終わる。待たせないのは、生成が 1 件 5 分弱で上限の件数ぶん続き、朝バッチの purge・backup を遅らせるため。先の実行が同じ台帳から生成・公開・送信を終えるので、後の実行が何もしなくても取りこぼさない(先の実行が失敗すれば、その実行が知らせ、続きは次の実行が台帳から再開する)。
  - LLM の待ちの間は SQLite の書き込みのトランザクションを持たない(記帳は生成の後の短いトランザクション。poller と DB を共有するため)。§4 の公開のロック(`dig-publish.lock`)はこのロックの中でだけ取る。入れ子の順はこの 1 通りで、`dig.lock` は待たないので、公開のロックを握ったまま見切ったスレッドが残っていてもデッドロックしない(公開のロックの待ちには上限がある)。
- 制約の根拠: 実行時間(デモ実測で 1 件 5 分弱。dig 段は deliver の後なので配信と watchdog は遅らせないが、件数が増えるほど purge・backup の完了が遅れ、poller と DB を共有する時間が延びる。設計 05 §1.1)と読む側の供給量(1 日に消化できるドラフトは 2〜3 本。未読ドラフトの山は未読負債の再生産であり本末転倒)。

## 4. 朝の調査段(ドラフト生成)

- 朝バッチに深掘り段を追加する。**実行主体 = 使い捨て `codex exec`(GH#105 で決定・2026-07-22)**。理由:
  - 調査段は本設計で**非対話のドラフト生成**に確定しており、app-server の本領(会話管理・ツール呼び出し・ストリーミング)が使われない。対話的な継続深掘り(§1 の第3フェーズ)はデスクで既存エージェントのセッションとして行うため、実装対象ですらない(カードへの質問への返事は ADR 0005 で signal-forge が持つことにしたが、1 問ごとの非対話の生成なので同じく使い捨て exec で足りる。GH#126)
  - analyze 段と同じ隔離レール(network 遮断・CODEX_HOME deny-read・書込遮断。#54)をそのまま使える。LLM にツールを持たせず、材料(DB の抽出本文)はプロンプト渡し・vault 書込と Telegram 送信は orchestrator(Python)の責務にすることで、下記の安全条件を構造的に満たす
  - app-server は experimental であり、常駐化は使い捨て CODEX_HOME の前提(memories 持ち越し = injection 持続経路の遮断)を壊す(2026-07-16 の検討と同根)
  - 外部リサーチ(関連リンク取得・外部照合)は v1 では持たない。「根拠の強さ」欄は本文内在の検証に限り、外部照合が要る主張は「未検証」と明記する。品質が不足するようなら allowlist 付き fetch 等を将来検討
- **別系統の AI のレビュー(GH#153。config `[dig].review`、既定 off)**: 書き手(Codex)のドラフトを Claude API(`anthropic-api`。設計 00 §5)が元記事と照らして読み、「元記事に無い主張」「読み違い(誤訳を含む)」「言い過ぎ」「欠かせない点の抜け」だけを指摘する(文体の好み・読み手の文脈に基づく推論の節・元記事の主張の正しさは見ない)。指摘があれば、書き手が元の指示 + 前回のドラフト + 指摘で **1 回だけ**直す(元記事で確かめられない指摘は採らない。直したあとの再レビューはしない)。コードの相互レビュー(author ≠ reviewer)と同じ考え方で、書いた AI 自身では気づきにくい誤りを拾う。
  - 査読者には元記事(書き手と同じ切り詰め)とドラフトだけを渡し、関心プロファイルと既存分析の要約は渡さない(元記事との照合だけをさせる)。ドラフトも untrusted data として nonce のフェンスで囲む。
  - **レビューは品質の上乗せで、失敗しても深掘りを止めない**: LLM の失敗(キーが無い・API の失敗・応答の形の崩れ)は未レビューのまま届け、ノートとカードに明示する。直すのに失敗したら直す前のドラフトを届け、指摘はノートに残す。実装の誤り(LLM の失敗以外の例外)は握らず item の失敗にする。
  - **ドラフトを予備の Claude が書いた回はレビューを省く(GH#180)**: 予備(設計 00 §5。`[llm_fallback]`)を有効にしていて Codex が失敗すると、解説のドラフトは予備の Claude API が書く。そのドラフトを Claude API がレビューしても同じ系統の点検で、別系統の照合にならない。そこで、ドラフトを実際に書いたエンジン(呼び出しの直後の FallbackEngine の `name`)を控え、レビュー役と同じならレビューを呼ばずに省く(費用も掛けない)。ノートとカードには、レビューの失敗と同じ出し方で「別の AI のレビューなし(下書きが予備の Claude のため)」と出す(月の上限より先に見るので、上限に達した月もこの表示になる)。台帳の `review_status` は月の上限で省いた回と同じ `skipped`。Codex が書いた回は変えない(指摘を受けた直しを予備が書いても、レビューは Codex のドラフトに対する別系統のもの)。
  - 費用: 呼び出しごとの見積もり額(やり直しの分を含む)を `dig_results.review_cost_usd` に残し、その月の合計が `[dig].review_monthly_cap_usd`(既定 $10)に達したら、その月はレビューを省く(1 本のレビューで上限を少し超えることはある)。doctor #9 の当月コストにも入る。送った後に応答の usage を受け取れなかった呼び出し(時間切れ・応答の切断・usage を読めない応答)は費用が分からないので、0 円にせず、課金されうる最大の額(入力 = プロンプトの UTF-8 のバイト数、出力 = `max_tokens` をそれぞれ単価で掛けた額。設計 00 §5 の予備と同じ。GH#241)で積む(費用が分からない呼び出しは多めに数え、上限の判定を実際の課金より少なめにしない。GH#323)。実額と見積もりは同じ列に合算し、分けて残さない。接続を張れなかった(送っていない)呼び出しと、API のエラーの応答(200 以外)は課金されない扱いで 0。月は doctor #9 と同じ UTC の暦月(上限の判定と doctor の表示で同じ額を見る。JST の月初の朝 9 時前は前の月に数える)。Anthropic のコンソール側の上限も併用する。
  - 1〜2 週間回して、指摘の中身(`dig_results.review_findings`。公開後も残す)を見て続けるかを決める(GH#153)。
- 安全条件は PROPOSAL §フェーズ2境界を継承する: read-only 基本・**書き込み先は vault の `SignalForge/DeepDive/` に限定**・送信/投稿/購入等の自動実行アクション禁止・untrusted 本文(取得した記事・gist 等)を起点とする実行はツール制限必須・long polling 維持。
  - **書き込み先の限定の実装(GH#204)**: `[obsidian].folder` は vault の中の相対パスに限る(絶対パス・`..`・空は設定の読み込みで拒む。設計 04 §7)。ノートの公開は、vault の実体(`vault_path` を resolve したもの。`vault_path` 自体は同期フォルダへのリンクなどの symlink でもよい)から DeepDive の置き場まで 1 段ずつ symlink を辿らずに開いたフォルダの中で書く。take の追記(§6)、返事の材料の読み取り(§7)、Daily / Items の export(設計 04 §7)、doctor #7 も同じ開き方をする(`app/vault_dir.py`)。途中のフォルダが外への symlink なら書かず、その件の公開の失敗にして本文を台帳に残す(次の実行で公開し直す)。公開するノートの名前に symlink などの通常のファイルでないものがあれば、辿らず置き換えず、既存のノートともみなさずに公開の失敗にする(既存とみなして本文を台帳から消すと、ノートの中身がどこにも残らないため)。ノートの名前は日付・item id・タイトル由来の slug(`/` などを除く)なので、記事のタイトルから DeepDive の外を指すことはない。
- **ノートの公開(GH#234)**: 生成物は先に台帳(`dig_results`)へ記帳し、ノートを vault に書き出してからカードを送る(設計 01 §7 末尾)。vault への書き出しには 1 件ごとに時間の上限(10 秒)を付ける。仕組みは返事と同じ(設計 05 §1.2・GH#145)。macOS のプライバシーの確認待ちで止まると、カードの送信も、朝バッチの purge・backup・失敗通知も止まるため。
  - 上限を超えたら、その実行では vault に触れない。その件と残りの件は、本文を台帳に持ったまま公開を未完にして先へ進む。公開済みの件のカードは送り、段は失敗として知らせる。未完の件は次の実行(朝バッチか `intel dig`)が公開してからカードを送る。
  - 見切ったスレッドは中断できず、後から書き終えることがある。次の実行が公開し、本人が take を書いたノートを、遅れた書き込みで置き換えないよう、公開にはロック(DB と同じ置き場の `dig-publish.lock`。flock)を使う。見切った実行は、そのスレッドが終わるまでロックを握る(プロセスが終われば外れ、スレッドも消える)。answer.lock(設計 05 §1.2)と同じ考え方。放す役はスレッドの終わりと実行の離脱のうち後になった側で、どちらが後かは 1 つの mutex の下で決める(見切りの判定の直後にスレッドが書き終えても、ロックが残らない)。見切った時にまだ書き始めていなかったスレッドは、後から動き出しても書かない。
  - ロックを 10 秒待っても取れない実行(前の実行が見切ったスレッドがまだ書き終えていないとき。実行どうしの重なりは §3 の排他で起きない。GH#196)は、公開を未完にして先へ進み、段は失敗として知らせる。あわせて、ノートを置き換える直前に同じ名前のノートが無いことを確かめ、あれば書かない。
- ブリーフの立て方:
  - **観点指定あり**: 指定された観点への答えを最優先の問いにする。
  - **自動選出(観点なし。🔖 新着と digest の上位。§3)**: 自動ブリーフ =「ユーザー文脈との接点を軸に、主張と根拠の強さを検証しながら読む」。ユーザー文脈の材料は当面は既知のプロジェクト文脈、将来は蓄積された知見ノート(知見が溜まるほど個人化される。ADR 0003 と整合)。

## 5. 成果物フォーマット

### 5.1 解説ノート(`kind: deepdive`)

- 置き場所: `SignalForge/DeepDive/`、ファイル名は Items 準拠の `YYYYMMDD-<item_id>-<slug>-深掘り.md`(日付は調査した日)。slug の作り方は Items と同じ(設計 04 §7)だが、原文タイトルが無い(X の投稿など)ときは分析の日本語の見出し(`analyses.title_ja`)から作り、どちらも無ければ `untitled`(GH#167)。Items と違ってノート名は台帳(`dig_results.note_name`)に残して引くので、規則を変えても既存のノートとの対応は崩れない。§5.2 の原文・対訳ノートも同じ slug を使う。
- frontmatter: `id` / `kind` / `title` / `url` / `author` / `published` / `requested`(観点 or 「観点指定なし: 自動キュー」。§3 の ③ で選んだときは「観点指定なし: digest の上位」。GH#349)/ `auto_brief` / `status`(作成時は `take待ち`。`take済` への書き換えは本人に任せる。take の記録の正本は台帳。§6)/ `related` / `previous`(同じ記事の前回の解説ノート。調べ直しのときだけ。§6・GH#137)/ `review`(別系統の AI のレビューの結果。§4 のレビューを使うときだけ。`clean` / `revised` / `revise_failed` / `failed` / `skipped`。GH#153)。
- 節構成(順序も含めデモで確定):
  1. **概要(2 方面)**: 「あなたにとって」(観点への答えの核心 + 自分の文脈への具体的含意)と「世の中にとって」(なぜ話題か・何が新しいか)。アウトカムベースで書く(キーワード羅列にしない)。
  2. **書き手の立ち位置**: 1 段落。誰が・どの立場・想定読者。主張の深さとスコープを読者が推定するための材料(デモで、立ち位置の推測が外れる実例により有効性を実証)。
  3. **骨子**(記事の論旨)
  4. **根拠の強さ(検証)**: 主張を鵜呑みにせず、数字の質・因果の強さ・利益相反を評価する常設欄。自動選出時ほど重要。
  5. **自分への接続**(signal-forge・自分の執筆・進行中の関心)
  6. **残った問い**(続き深掘りの候補)
  7. **ソース**(原文ノートへの wikilink 含む)
  - (§4 のレビューを使うときだけ)**レビューの記録**: take 領域の上に Obsidian の callout で置く。指摘があれば折りたたみで、1 件 1 行(🔴 must / 🟡 should・種類・場所・問題・直し方)。指摘なし・失敗・上限で省略は 1 行(GH#153)
  8. **take 領域**(手書き・追記はリプライ経由でも入る)

### 5.2 原文・対訳ノート(`kind: deepdive-source`)

- **日本語ソース**: 原文保全ノート(全文コピー・私的利用。本文の取得日と原典 URL を frontmatter に記録)。
- **英語ソース**: 対訳ノート — **日本語全訳を地の文にし、英語原文は節ごとの折りたたみ callout(`> [!quote]-`)に格納**。スマホでは日本語をすらすら読み、確認したい箇所だけ原文を開く。段落交互(EN/JA)はスクロール長が倍になるため採らない。
- ファイル名: 日本語ソースは `YYYYMMDD-<item_id>-原文-<slug>.md`、日本語以外のソースは `YYYYMMDD-<item_id>-対訳-<slug>.md`(ツイート本文だけのものは作らない)。
- frontmatter の `fetched`(原文・対訳ノートの両方)は、本文(`documents.extracted_text`)を取得・抽出した日で、`documents.extracted_at` の JST の日付(`YYYY-MM-DD`)。深掘りした日ではない(GH#239)。数日前に取った本文を初めて掘るときや、保持期間の中で調べ直すときにも、本文の古さが分かるようにするため。深掘りした日はファイル名の日付で分かる。
- 日本語かどうかは深掘りのときに本文(`documents.extracted_text`)から判定する: 引用(「」『』“” の中。入れ子も含む。英語の `"…"` は同じ行の中の組)を除いた地の文の語の数で比べ、日本語の語(ひらがな・カタカナ・漢字の、文字種ごとの連なり)がそれ以外の語(英単語・コードの識別子など)より多ければ日本語。ただし日本語の文字のうちかなが 2 割に満たなければ日本語にしない(漢字だけの中国語を外す)。文字の数でなく語の数で比べるのは、英単語やコードの多い日本語の記事を取りこぼさないため。引用を除くのは、長い日本語の文を引用する英語の記事を引用の語の数で日本語にしないため(日本語の記事は引用を除いても地の文が日本語のまま残る)。英語の記事を日本語と誤ると対訳が無くなるので、語の数が同じものや、コードが本文より多い日本語の記事のように迷うものは日本語以外(対訳)に倒す。`documents.language` は本文抽出で書いておらず、値が NULL のときに日本語以外と扱うと日本語の記事まで対訳に回るため(GH#173)。`documents.language` に値があればそれに従う。
- 原文を別ノートに分けるのは解説ノートの読み心地を守るため(デモ 1 周目の設計発見)。
- **X 本文非保持ポリシー(GH#2)の例外条件**: ツイート原文全文の恒久保存は行わない。Web 記事・gist は私的利用の範囲で全文保全・対訳可。ライセンス上の注意があれば frontmatter に記す。

### 5.3 Telegram 概要カード(1 通・分割しない)

構成(v3。デモ 2 周のフィードバックで確定):

```
🔎 深掘り #<item_id>「<日本語訳タイトル>」(<原題・原語のとき>)
✍️ 書き手: <立ち位置 1 行>
<選出ラベル: 観点「…」 / リプライ指定・観点なし / 🤖 自動選出(🔖新着)・観点なし / 🤖 自動選出(今日の digest の上位)・観点なし>

あなたにとって
<アウトカムベース 3〜5 行>

世の中にとって
<3〜4 行>

📄 ノート: SignalForge/DeepDive/<file>(対訳ありの場合はその旨)
💬 リプライで質問すると答えます。感想・結論は take として記録します

[ 🔗 元記事 ] [ 📝 要約 ] [ 📖 詳しく ]
```

- **ボタン(GH#141)**: スマホの Telegram からは Obsidian のノートも元記事も開けないので、カードにボタンを付けて Telegram で完結させる。🔗 元記事は URL ボタン(正規化した URL。http(s) の ASCII の URL のときだけ。不正な URL で送信自体が失敗しないように)。📝 要約(元記事が日本語以外なら和訳した要約)と 📖 詳しく(カードより詳しい説明)は、押すと質問と同じ流れ(§6・`intel answer`)で返事をカードへのリプライとして送る。返事をしない設定(`answer_daily_cap = 0`)では 🔗 元記事だけ。既に送ったカードには付けない

- §4 のレビューを使うときは、📄 ノートの行の前にレビューの結果を 1 行出す(固定の文言だけ。「🧪 別 AI のレビュー: 指摘 2 件 → 直した版です」「⚠️ 別 AI のレビューに失敗(未レビュー)」「⚠️ 別の AI のレビューなし(下書きが予備の Claude のため)」など。GH#153・GH#180)。
- 末尾の案内は質問への返事(GH#126)の有無に合わせる。`[dig].answer_daily_cap = 0`(返事をしない)のときは「💬 リプライは感想として記録されます」(LLM が分けないので take としては記録しない。§6)。

- 選出ラベルは、そのカードをどの経路で選んだかを示す(§3 の優先順位)。③ の digest の上位から選んだときは「🤖 自動選出(今日の digest の上位)・観点なし」にし、🔖 新着の自動選出と見分けられるようにする(GH#349)。夜の一覧で予定に出なかったカードが朝に届いた理由も、このラベルで分かる(§2)。
- タイトルは必ず日本語(英語原題は括弧で併記)。`analyses.title_ja` があれば再利用。
- 「あなたにとって / 世の中にとって」の 2 方面は読む・読まない判断の材料。「世の中的に大事だが自分には遠い」の未読を正当化できる。

## 6. take と接続

- カードへのリプライは GH#96 の感想リプライ基盤が受け、**take(結論・感想・評価)** と **続き要求(質問・追加の観点)** に分ける。分け方は、返事を作る呼び出しとは別の、本人の入力だけを渡す**意図の判定**の LLM 呼び出し(プロンプト dig-intent-v001)が種類(`question` / `take` / `both`)を返す(台帳 `dig_questions.kind`)。GH#106 はその分類を使って take を記録する。一つのリプライに両方が含まれてよい(デモ 1 周目のリプライは「判定軸に興味を持った(take)+ そこを読み込みたい(続き要求)」の複合だった)。
  - **意図の判定を返事から分ける(GH#245)**: take の記録と調べ直しの依頼は書き込みを伴う操作なので、外部由来の材料(概要カード・解説ノート・原文/対訳ノート・元記事の本文)とそれから作った返事(それまでのやり取り)を読む返事の呼び出しの出力では決めない。判定には本人の入力だけ(リプライの本文と、返信先が失敗の知らせか)を渡し、材料の中の文が判定を動かせないようにする。当初(GH#126・GH#137)は、返事の呼び出しが返事と一緒に種類と調べ直しの依頼かも返していた(別の呼び出しを増やさない)。それでは材料からの誘導で、本人の質問が take として記録されたり、求めていない調べ直しが積まれたりしうるため改めた。疑問符や語尾の規則では「〜が気になる」のような自由文の take と質問を分けきれず、質問を take(確定した知見)として書く誤りが増えるので、規則ではなく LLM の別の呼び出しにする。
    - 返事の呼び出しと同じエンジン・同じ effort(`answer_reasoning_effort`)で、返事より先に呼ぶ。1 日の上限(`answer_daily_cap` は質問の数)と予備のエンジンの台帳(段 `answer`)も返事と共有する(1 件あたりの LLM 呼び出しは 2 回になる)。
    - 判定に失敗したら返事も作らず、返事の失敗と同じく失敗の知らせを送る(take・調べ直しの依頼を黙って落とさない)。カードのボタンからの依頼は判定を呼ばない(下)。
  - **take**(`take` / `both`)→ ノートの take 領域へ追記 + `followup_dig` に記録(GH#99 の既知境界「ブックマークの消化動線」をここで閉じる)(GH#106)。
    - 記録は `intel answer` が返事を送った後に行い、返事を送れた行だけを記録する(本人を待たせない。返事が届く前に未消化一覧から消さない)。ノートに書くのは**本人のリプライの原文**だけで、LLM の返事は書かない(確定するのは本人の take だけ = ADR 0003)。`both` もリプライ全体を書く。
    - 書き方: 解説ノートの末尾(手書きメモ・take 領域)に「**take**(JST の日時・Telegram のリプライ)」の見出しと原文を足す。見出しに記録番号(質問 id)を入れ、やり直しで 2 回書かない(途中まで書いて止まっていたら続きだけを足す。書きかけの後ろに別の内容が続いていたら、節を丸ごと足す。印に HTML コメントを使わないのは、途中で止まると閉じていない `<!--` が残り、その後ろが隠れるため)。書き込み先は、本人が設定した vault を起点に、その下のフォルダを 1 段ずつ symlink を辿らずに開いて決める(途中のフォルダが外への symlink なら、ノートへの追記を諦める。外には書かない)。公開済みのノートは本人のもの(Obsidian で開いて編集していることもある)なので、**末尾への追記(O_APPEND)だけ**を行い、ファイルを書き直さない。追記は今ある中身に触れないので本人の編集を消すことは無く、エディタが古い内容で保存し直したときに消えうるのは足した take だけ(原文は台帳と item_notes に残る)。frontmatter の `status` は書き換えない(1 行だけを書き換えるにはファイルを書き直すしかなく、本人の保存と競合したときに編集を消しうるため。2026-10-19 に、書き直して競合を検出する方式を 3 回試して見直した)。本人が手で `take済` にしてよい。
    - `followup_dig` は最新の行が `yes` でないときだけ `yes` を記録する(深掘り済みなら足さない。追い掛けで「いいえ」に訂正した後の take は `yes` を足し、一覧から消す。GH#195)。take を受け付けた後に本人が追い掛けで「いいえ」と答えていたら、`yes` を足さない(返事を作る間や vault の障害で記録が遅れても、遅れた古い take で本人の後の回答を上書きしない。ノートへの追記と台帳の記録は行う。GH#336)。先後は受付の順序で見る。質問を受け付けた時点で記帳済みの signals の id の最大を印に残し(`dig_questions.received_signal_id`。migration 025)、最新の `followup_dig` の id がそれより大きければ受付の後の回答とみなす(時刻は同じ秒の先後が分からないので使わない)。signal_date は 🔖 の reaction と同じ配信日、🔖 の無いアイテム(X のブックマーク・自動キュー・digest の上位からの自動選出。§3)は take の日。
    - 台帳 `dig_questions.take_recorded_at`(migration 013)で記録済みを判定する。vault に書けない一時的な失敗(DeepDive の置き場ごと見えないときを含む)は記録しないまま残し、poller の見回りが送れていない返事と同じ間隔(10 分)で `intel answer` を起動して再試行する。vault が応答しない(macOS の確認待ちなど。時間の上限 10 秒)ときも記録しないまま残し、その実行の残りの take は試さない(GH#145)。ノートの見出しの記録番号で 2 回書かない。本人がノートを動かした・消したときは、ノートへの追記だけを諦めて `followup_dig` は記録する(原文は台帳と item_notes に残る)。時間の上限を超えたとき以外の失敗はその 1 件に閉じ、後の take は記録する。
    - 1 日の上限(`[dig].answer_daily_cap`)を超えたリプライと、上限 0 のときのリプライは LLM が分けないので、take としては記録しない(感想 item_notes にだけ残る)。
  - **カードのボタン(GH#141)** → 📝 要約・📖 詳しく は決まった依頼文を台帳に積み、質問と同じ流れで答える(1 日の上限も共有。同じカードの同じボタンは 1 回だけ)。材料は概要カードと**元記事の本文(DB の `documents`)**で、vault のノートには頼らない(保持期限を過ぎて DB に無いときだけ原文/対訳ノートを使う)。返事は本人の take でも調べ直しの依頼でもないので、意図の判定を呼ばず、take としては記録しない。
  - **続き要求** → 質問にはその場で答える(Telegram のリプライで返事。ADR 0005・GH#126)。観点を足して調べ直してほしいものは**続きの観点**として翌朝のキューに積む(GH#137)。
    - 見分け方: 意図の判定(上の GH#245)が、種類と一緒に「調べ直しの依頼か」(`redig`)を返す(プロンプト dig-intent-v001)。その場の返事で足りる質問・感想は依頼にしない。ボタン(📝・📖)からの依頼は調べ直しにしない。
    - 観点は**本人のリプライの原文**(LLM の出力は使わない。材料の外部本文が、翌朝の深掘りの指定観点 = プロンプトの信頼される側に入らないようにするため)。
    - 積み方は未消化一覧へのリプライ指定と同じ(`dig_queue` を `queued` へ戻し、`requested_at` を更新して優先し、観点を上書きする。`source` は変えない。設計 01 §7)。1 日の上限は `[dig].daily_cap` を共有し、本人の指定として自動選出より先に掘る。`daily_cap = 0`(深掘りの段が止まっている)ときは積まない。返事と依頼は 1 つのトランザクションで記録し、積めたときだけ返事の末尾に「次の朝の深掘りで調べ直します」と知らせる(台帳 `dig_questions.redig`)。
    - 受け付ける前に、翌朝の調査段が材料に読む元記事の本文があるかを確かめる(GH#197)。条件は調査段の選定と同じ(§3 の材料不足。`documents` の本文が `[dig].min_body_chars` 字以上)。掘った記事には本文があったので、無いのは保存の期間を過ぎて purge で消えたとき。そのときは積まず、翌朝の実行を約束せずに、返事の末尾に「元記事の本文の保存の期間が過ぎて材料が無いため、この記事は調べ直せません」と知らせる。保存済みの原文/対訳ノートで調べ直す経路や、本文を取り直す経路は足さない(X の本文を保持しない方針を変えないため。GH#2)。朝バッチは dig 段の後に purge 段なので、受け付けた時点の本文はふつう翌朝の深掘りまで残る。上限の件数で掘るのが延びる間に消えたときは、§3 の材料不足として 1 回知らせて指定を外す。
    - 返事を作る間(リプライから返事が届くまでの数分)の本人の操作を、作り終えた古い依頼で上書きしない(GH#235)。質問を受け付けた後に、本人が未消化一覧でそのアイテムをパス・指定し直していたら、依頼は積まず、知らせも付けない(返事は送る)。照合は受付の順序で行う。未消化一覧への操作は、反映した時点で受け付け済みだった質問の id の最大を印に残し(`dig_queue.backlog_op_question_id`。migration 022)、質問の id がそれ以下なら古い依頼とみなす。時刻(秒の単位)は同じ秒の先後が分からないので使わない(poller が溜まった update をまとめて処理すると、質問とパスが同じ秒に入りうる)。先の調べ直しの依頼と朝の深掘りの `done` は印を変えない(続けて送った調べ直しや、掘った後に届いた調べ直しは積む)。
    - 結果は**新しい解説ノート**と新しいカードで届く。前回のノートは書き換えず、新しいノートの `previous` で前回へつなぐ(公開済みのノートは本人のもの。take の付いたノートに AI のドラフトを混ぜない = ADR 0003)。
    - take としては記録しない(続き要求は結論ではないため)。`both` に調べ直しの依頼が含まれていれば、take の記録と両方を行う。
- 確定と未確定: **知見として確定した扱いになるのは take が付いた部分だけ**であり、take のないドラフトは AI ドラフトのまま(ADR 0003 の「AI ドラフト + ユーザー take だけ確定」と整合)。take が付いたかの正本は台帳(`dig_questions.take_recorded_at`)で、ノートには take の節(見出しに記録番号)が残る。retrieval 側はこれで確定/未確定を判別する(frontmatter の `status` は作成時の `take待ち` のまま。本人が手で書き換えたときはその値を尊重する)。
- デスクでの対話(継続深掘り)の成果は、解説ノートに**続章として還流**する(知見 = 深掘りの副産物。ADR 0003)。
- **KPI 非接続原則**: take の中身を KPI・ランキングへ自動接続しない(2026-07-18 の判断と同根。測定定義を汚さない)。take と一緒に記録する `followup_dig = yes` は「深掘りした」の記録なので、🔖 の付いたアイテムでは KPI 06(フェーズ2境界の深掘り実施率)の分子に入る。🔖 の無いアイテム(X のブックマーク・自動キュー・digest の上位からの自動選出)は KPI 06 が数えない(分母が 🔖 の累計のため)。

## 7. 実装分割

レビュー可能な単位で 3 分割し、ADR 0005 で 4 の質問への返事を追加した(段階導入の位置づけは PROPOSAL §フェーズ2境界 2026-07-19 改訂を参照。軽量段の検証はデモで代替済みのため、①は入口のみ・②でフル調査段を実装する):

1. **夜の入口**: 深掘りキュー(スキーマ)+ 自由文リプライのパース(番号 + 観点 / パス)+ 未消化一覧との接続
2. **朝の調査段**: 上限 N 件の実行制御 + ドラフト生成 + DeepDive ノート出力 + 概要カード配信
3. **take 記録**: カードリプライ → take 領域追記 + followup_dig 記録(GH#106)+ 続き観点の登録(GH#137)
4. **質問への返事**(ADR 0005 で追加): カードへの質問 → ノートと原文を材料に答えを作り、Telegram のリプライで返す(GH#126。3 より先に作る)

GH#349(候補の補充と状態の見せ方)は、レビューできる小さな PR に分けて次の順で進める。届かない朝を先に無くし、見せ方とボタンはその後に足す。

1. **digest の上位から埋める**(§3 の ③): `dig_queue.source` に `digest` を足す migration、③ の選定、write-ahead と同じトランザクションでのキューの行(生成中にできた行との競合の規則を含む)、カードの選出ラベルと frontmatter の `requested`(§5)。
2. **候補の無い朝の知らせ**(§3): 1 行の知らせ(中断した分のカードを送った実行では送らない)と、同じ日に 2 回送らない印。③ の後に入れる(先に入れると、③ で埋まる朝にも知らせが出る)。
3. **一覧の各行の状態と明朝の予定**(§2): 選定の規則を、朝の段と夜の一覧が同じものを呼べる形(delivery 層に依存しない `app/dig.py` の側など)にまとめ、各行の印、予定の行、入れ替わりと digest で埋める旨の 1 行を出す。書き込みは無い。選定の規則は `app/dig.py` の `select_from_queue` にまとめた(細目は §2)。
4. **skip のボタン**(§2): callback_data(設計 04 §3)、一覧のメッセージの照合、パスの反映、盤面の更新。3 の予定の行が前提。

Obsidian vault のモバイル同期は運用前提から外した(ADR 0005)。スマホでノート全体を読む面は中央アプリで解き、それまでは PC で読む。

- 質問への返事の起動 = poller がカード・その返事へのリプライを台帳に積み、`intel answer` を別プロセスで起動する(受信を LLM の待ちで止めない。設計 05 §1.2)。リプライは感想としても従来どおり item_notes に記録する(take の記録 GH#106 の後も続ける。item_notes は質問・上限超えを含む全リプライの記録。後から付いた感想で Items ノートを書き直す追いパスの対象は、digest に記事メッセージとして載った item だけなので、🔖 保存節にだけ載った X ブックマークなど、それ以外の item へのリプライは item_notes に残るがノートには出ない(その日の digest を export し直したときを除く。設計 04 §5・§7)。解説ノートの take 領域は確定した結論だけ)。1 日の上限は `[dig].answer_daily_cap`(既定 20。超えた日・0 は記録だけ)。カード末尾の案内は返事の有無に合わせる(GH#126)
- 質問への返事の本体 = `intel answer`(GH#126)。台帳 `dig_questions`(設計 01 §7 末尾)に積まれた質問に古い順で答え、本人のリプライへの返信として送る。材料は概要カード(台帳)・解説ノートと原文/対訳ノート(vault から読む。vault の実体から DeepDive の置き場まで symlink を辿らずに開き、その中の通常のファイルだけを読む。途中のフォルダやノートが symlink なら読まず、見つからない扱いにする(§4。GH#204)。見つからなければ注記して手元の材料で答える)・同じカードのそれまでのやり取り(直近 5 往復。答えを作れなかった回は、返事の代わりに「回答失敗」の決まった文を置く。GH#236)。take・調べ直しの依頼かは、材料を渡さない別の呼び出しで判定する(§6。GH#245)。答えを作る部分(`app/dig_answer.py`)は送信を注入で受け、操作面に依存しない(ADR 0005)
- 失敗の知らせ(「答えを作れませんでした。時間をおいて、もう一度リプライしてください」)へのリプライ(GH#236) = 答えられなかった元の質問に結び付け(台帳 `dig_questions.retry_of`。poller が返信先の message_id から引く)、「もう一度」のような短いリプライでも、元の質問を今回のリプライに添えて返事の材料に渡す。やり直しも失敗し、その知らせにまたリプライしたときは最初の質問まで辿る(最初の質問は必ず渡し、途中のやり直しは直近の分だけにして合わせて 5 件まで。直近 5 往復から外れていても渡す)。元の質問がボタンからの依頼なら、材料もボタンと同じ(元記事の本文)にする。意図の判定(§6)には、返信先が失敗の知らせであることだけを渡し、元の質問は渡さない。take として書く原文と調べ直しの観点は今回のリプライの本文なので、判定も今回の本文で行う(元の質問の take・調べ直しは引き継がない。感想としては item_notes に残る)
