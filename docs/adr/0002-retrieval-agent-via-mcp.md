# ADR 0002: retrieval の主経路は「エージェント経由(MCP)」とする

- ステータス: Accepted(2026-07-12)
- 関連: フェーズ2(B: 貯めた知見を活かせる状態)/ ADR 0001(興味フィードバックループ = 入力側)/ `CONTEXT.md`

## 背景・決定

フェーズ2の北極星は retrieval(課題に直面したとき、過去の関連知見を引けること)。当初は「ユーザーが検索窓で引く(プル型)」を想定したが、痛みの核心は「貯めるほど**見たことすら忘れる** = 思い出せないと検索しにいけない」点にある。またユーザーは今後の作業を基本的に AI エージェントと進める。

そこで retrieval の主たる利用者を、ユーザーの検索窓ではなく **ユーザーと作業する AI エージェント(MCP 経由で知識ベースを問い合わせる)** と定める。**不変条件: エージェントは作業文脈から自発的に retrieval を検討する ── ユーザーが保存物を想起・指定しなくても引く。** これが無いと「思い出して検索する」に戻り、却下した検索 UI と同じ痛み(見たことすら忘れる)を解けない。ユーザーから見れば知見が差し出される(push)、仕組みとしてはエージェントが引く(agent-pull)。人間向けの検索 UI は主経路にしない。

## なぜ / トレードオフ

- **却下案**: 人間向け検索 UI を先に作る。→ ユーザーの実際の働き方(常にエージェントと)に合わず、UI の構築・保守コストを負う。かつ「思い出して検索する」前提のままでは痛みを解けない。
- **採用の利点**: (1) 働き方に一致 (2) 検索 UI を作らずに済み MVP の作る面が一つ消える (3) 知識ベースが Signal Forge 専用でなく**全プロジェクト横断の個人メモリ**になる(どのエージェントセッションからでも引ける) (4) 既存の蓄積(Obsidian)を MCP で問い合わせ可能にする自然な延長として実装できる。
- **代償(明示)**: service-pull 化しても精度要求は下がらず**上がる**。エージェントの文脈は有限で、ノイズや出典不備の retrieval は一度で信用を失う。「返す中身の質と出典」が中核課題になる。

## 未決(この ADR の射程外)

- retrieval の対象 substrate(Obsidian の蓄積か、DB か、別ストアか)
- retrievable な単位(元記事のみか、ユーザーの所感込みか)
- 自発 retrieval の**具体的な発火条件**(どんな作業文脈でツールを引くか・ツール発見性の作り込み)/ 1 問い合わせの返し方(件数・粒度・出典形式)。※「自発的に検討する」こと自体は上で決定済みで、未決は発火条件のみ
