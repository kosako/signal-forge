# ADR 0001: 興味フィードバック・ループと X ソース戦略

- ステータス: Accepted(2026-07-10)
- 関連: 設計 02 §2(X コネクタ)/ 設計 03 §4(関心プロファイル)/ PROPOSAL §情報源 / Issue #1(Day 0 ゲート)
- 上位文書: `docs/PROPOSAL.md`(企画正本は Notion。本 ADR は覆りにくい設計判断の記録)

## 背景

Issue #1(Day 0 X 実測)で実効単価を測ったところ **≈ $0.0040/件**($1.86 / 470件)だった。楽観前提 $0.001 の約4倍で、ホームTL は流量が多く(昼 ~100件/時)、月$20 の予算内(`daily_read_cap` ≈ 130)では**毎朝およそ直近1.5〜2時間ぶんしか読めない**ことが判明した。

この制約下で「何を取り込み、どう選別するか」を検討した結果、当初検討した**厳選アカウントリスト方式**には「継続的な手動メンテナンス」という致命的な弱点があると分かった。リスト保守は、本プロジェクトが削ろうとしている「巡回の手間」を「管理の手間」に付け替えるだけになる。

## 決定

キュレーションを**手動のソース管理ではなく、ユーザーの自然な行動を燃料にした自己更新ループ**で行う。

### 興味シグナル(興味モデルへの入力)

| シグナル | 意味 | 強さ |
|---|---|---|
| X 🔖 ブックマーク | 意図的に「後で」保存 | 強・正 |
| X 🔁 自分の RT | 是認・拡散 | 強・正 |
| X ❤️ 自分のいいね | 弱い関心・儀礼的も混じる | 弱・正 |
| Telegram 👍 価値あり | 提示済みへの肯定 | 中・正 |
| Telegram 🔖 深掘りしたい | 提示済みへの強い肯定 | 強・正 |
| Telegram 👎 不要 | 提示済みへの否定 | 中・**負** |
| Telegram ✅ 既知 | 分類は成功だが新規価値0 | 中立(興味の符号なし。dedup/校正の材料) |

- **符号**: 正シグナルは興味モデルを引き上げ、👎(負)は引き下げる。✅ は興味方向には中立(既知として扱う)。
- **🔖 は2種類あり別物**: X の🔖ブックマーク(自分が X 上で保存した興味シグナル=探索)と、Telegram の🔖ボタン(システムが提示したアイテムへの「深掘りしたい」=活用)。両方とも強い正シグナルだが出所が違うので分けて記録する。
- 探索(X の 🔖/❤️/🔁 = システムが未提示のものを自分で発見)と活用(Telegram 反応 👍🔖✅👎 = 提示済みへの評価)を**区別して扱う**。
- 重み = **種類の重み × 直近の重み**。興味は時間変化する(「今これが知りたい」)ため、**固定プロファイルではなく直近を重く見る移動平均**とする。係数は config で調整可能にする。

### 興味モデルが駆動するもの

1. **検索(`search/recent`)**: キーワードは **3スロット固定**。増やさず**入れ替え式**(「今の最重要3つ」を強制的に選ばせ、クエリの発散を防ぐ)。**スロット固定はクエリの本数を止めるだけでコスト上限にはならない**(各スロットの取得件数が読取を消費する)ため、コスト上限は下記「予算配分」で別途固定する。
2. **ホームTL(フォローフィード)**: cap 小(既定 130/日)。偶発的発見枠。**朝1回取得**(時間分散サンプリングは後日の強化項)。
3. **フォロー推薦**: ブックマーク/いいね/RT に頻出する人を推薦候補として提示。

### 予算配分(月 $20 以内)— コスト上限は「読取件数」で固定する

Day 0 実測(実効単価 ≈ $0.004/件)を前提に、**X の読取は「ホームTL + 検索」を合算した日次上限で管理する**。3スロット固定はクエリ本数の上限であって金額上限ではない。

- **ハード上限**: 合算日次読取 **≦ 165件/日**($0.004 × 165 × 30 = **$19.8 ≤ $20**)。$0.004 前提の理論上限は 166件/日($19.9)なので 165 で余白を取る。
- **初期配分**: ホームTL `daily_read_cap = 130`(月 ~$15.6)/ 検索 **35件/日**(3スロット × 約12件。月 ~$4.2)= 合算 165件/日。
- **単一ノブ**: S0 実装(#57)で「ホームTL + 検索の合算日次読取上限(165)」を config の単一ノブにし、超過ペースは doctor #9 のコスト集計で WARN する。ホーム/検索の内訳(130 / 35)は運用しながら再配分する(合算 165 を超えない)。
- **S1 以降**: ブックマーク/いいね/自RT 取込も読取を消費するため、同じ月次予算($20 の X 枠 = 合算 165件/日)の内側で cap を再配分する(取込を足すぶんホーム/検索を削る)。

### 原則: チューニングは「提案 → 人が承認」(人間ゲート)

**お金を使う変更(検索スロット更新)とアカウントへの書き込み(フォロー)は、システムが週次レビューで提案し、人が承認する。** 自動でのスロット増加・自動フォローはしない。理由:

- **コスト**: 検索クエリが広がると `search/recent` 消費と月次上限に跳ねる
- **ドリフト**: 自動更新は的が徐々にズレる・過学習する
- **書き込み副作用**: 自動フォローは X アカウントへの事故リスク

## X ソースと認証

| ソース | エンドポイント | 認証 | 段 |
|---|---|---|---|
| ホームTL | `/2/users/:id/timelines/reverse_chronological` | OAuth 1.0a(既存4キー) | S0(#15) |
| AI 検索 | `/2/tweets/search/recent` | OAuth 1.0a / Bearer | S0(新コネクタ) |
| ブックマーク | `/2/users/:id/bookmarks` | **OAuth 2.0(PKCE, `bookmark.read`)必須** | S1 |
| 自分のいいね | `/2/users/:id/liked_tweets` | OAuth 1.0a も可(実装では OAuth2 に寄せる) | S1 |
| 自分の RT | `/2/users/:id/tweets` | OAuth 1.0a(既存) | S1 |

- **ブックマークだけが OAuth 2.0 必須**(API 上の制約)。いいね・自RT は OAuth 1.0a User Context でも取れるが、**S1 では OAuth 2.0 に統一する(実装選択)** — ブックマーク用に組む OAuth2 に相乗りさせ、認証経路を1本に保つため(API 上の必須条件ではない)。
- 検索・ホームTL・自RT は OAuth 1.0a / Bearer で足りる(OAuth 2.0 不要)。tier の月次上限は S0 実装時に要確認。

## 段階化(一気に作らない)

| 段 | 内容 | 対応 Issue | 性質 |
|---|---|---|---|
| **S0** | ホームTL(cap 130)+ AI 検索(固定シード語・3スロット)→ 既存パイプライン(digest + 反応は稼働済み)。新認証なし | **#15**(ホームTL)+ **#57**(AI 検索) | 出荷可能な最小 |
| **S1** | OAuth 2.0 + ブックマーク/いいね/自RT 取込(興味シグナル)+ 週次レビューに**インサイト表示**(頻出テーマ・常連著者・読取専用) | **#58** | 安い・高価値・ドリフト無し |
| **S2** | 週次レビューが**検索スロット更新案 + フォロー推薦を提示 → 人が承認** | **#59** | 人間ゲート付きチューニング |
| **S3(未定)** | 提案が信頼できると分かれば自動度を上げる | 後日起票 | 後日判断 |

- **S1 の範囲を一意化**: S1 は**興味シグナルの収集 + 週次インサイトの可視化(読取専用)まで**。移動平均の興味モデルは S1 で**土台のデータを貯める**が、その値で**検索スロット・フォロー・ランキング係数を自動変更することはしない**(自動チューニングは S2 で人間承認を挟んで初めて起きる)。よって PROPOSAL「MVP はスコア自動調整をしない(記録のみ)」と矛盾しない。
- ループは各段の出荷を通じて**データから創発**させる。S0 の時点では興味モデルは既存の関心プロファイル + Telegram 反応のみ。

## 将来のソース拡張(backlog・今は作らない)

- **Reddit / Facebook 等**の自分のタイムライン・保存を API で取り込み、ソース種別を分けて扱う構想がある。コネクタは source プラガブル(設計 02 §1)で興味ループもソース非依存のため、構造上は載る。
- **各プラットフォームは X と同様に「着手前の実測ゲート」を必須**とする(単価・権限・取得範囲が前提と異なりうる。X で実証)。
- 実現性の見立て(要ゲートで確認・確認日 2026-07-10): **Reddit は saved/home の技術的エンドポイントは存在するが、API 利用に明示的なアクセス承認が要る(Responsible Builder Policy)ため、承認取得が主要リスク**。**Facebook は現行の公開 Graph API でホームフィード読取が困難**(`user_posts` は自分の投稿のみ。ホームフィード読取パーミッションは提供されていない)。いずれも一次資料と最新ポリシーをゲートで再確認する。

## 影響

- **設計 02 §2**(X コネクタ): エンドポイントが「ホームTLのみ」から「ホームTL + 検索」に拡張。rate limit は実測 180/15min(旧記載 5/15min は誤り)。ノイズ対策の主軸が「ソース選別」から「興味モデルによるランキング + 3スロット検索」に移る。**本 ADR 確定に合わせて 02 §2 を同期する(本 PR で追従)**。
- **設計 03 §4**(関心プロファイル): 静的プロファイルから、行動シグナル駆動の**移動平均**モデルへ拡張(S1 以降)。ただし S1 は収集・可視化まで(自動反映は S2)。
- **`sources` テーブル**: 将来の Reddit/Facebook 追加時に type enum の拡張(マイグレーション)が要る。
- **H2(X アカウント方式)決定**: **手動維持のアカウントリストは作らない**。ホームTL(偶発)+ AI 検索(注力)+ ブックマーク/いいね(S1 シグナル)で回す。

## 却下した案

- **厳選アカウントリスト方式**: 継続的な手動メンテナンスが本プロジェクトの目的(手間削減)に反する。リストが埋めるはずだった「注力キュレーション」は、検索クエリ(3スロット)+ ブックマーク + フォローで代替でき、いずれも低メンテ。
- **検索スロット無制限追加**: コストと的の両方が崩れる。3枠固定・入れ替え式で防ぐ。
- **興味チューニングの完全自動化**: コスト・ドリフト・書き込み副作用のため、人間ゲート(週次承認)を挟む。
