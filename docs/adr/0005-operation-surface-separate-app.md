# ADR 0005: 機能は signal-forge が口として持ち、操作するアプリは別プロジェクトで作る(当面の操作面は Telegram)

- ステータス: Accepted(2026-10-18)
- 関連: ADR 0002(retrieval の主経路 = MCP)/ ADR 0004(深掘りは既存エージェント内・専用 UI は延期)/ 設計 06 / GH#123(操作面の方針)/ GH#126(質問への返事)/ GH#106(take 記録)

## 背景

- 2026-10-17 のユーザーフィードバック(GH#123): 配信の質はおおむね良いが、深掘りを通知(Telegram)から完結できず、PC で Obsidian を開く必要がある。最終的には 1 つの面で完結したい。
- 実データ(2026-07-21〜10-17): 概要カード 31 通のうち観点指定は 5 通。カードへのリプライ 3 件のうち 2 件は質問(続き要求)だが、今は感想として記録するだけで返事が無い。take 済みのノートは 0 件(GH#106 未実装)。
- 深掘りの段ごとの場所: 夜の指定・概要カード・take のリプライは Telegram で完結する。解説・対訳を読むのは PC の Obsidian、質問(続きの対話)はデスクのエージェントで、スマホだけでは完結しない。
- 個人サービスが signal-forge のほかにも増えており、通知や操作の出口がサービスごとに違う。

## 決定

1. **機能は signal-forge が口(インターフェース)として持ち、それを操作するアプリは別プロジェクトで作る。** 操作アプリは signal-forge 専用ではなく、他の個人サービスも束ねる中央アプリとして signal-forge の外で構想する。作り方(Web アプリかネイティブか)やスマホから Mac への届け方は、そのプロジェクトで決める。
2. **signal-forge は操作面を差し替えられる形を保つ。** Telegram への依存は `app/delivery/` に閉じたままにし、新しい機能(質問への返事など)も、中身を操作面に依存しない関数として作る。中央アプリへ出す口は ADR 0002 の MCP の方向で、出すときに改めて決める。
3. **当面の操作面は Telegram**(通知・夜の指定・take・質問への返事)。中央アプリができるまで、Telegram が口の最初の利用者になる。
4. **カードへの質問にその場で答える機能を Telegram で先に作る**(GH#126)。後で中央アプリに差し替わるのは Telegram につなぐ部分だけで、答えを作る部分はそのまま使う。
5. **知見の置き場は Obsidian のまま**(ADR 0004 を維持)。スマホでノート全体を読む面は中央アプリで解く。それまでは概要カードと質問への返事で補い、ノート全体は PC で読む。設計 06 §7 の運用前提だった vault のモバイル同期は前提から外す。

ADR 0004 との関係: 「専用 UI は延期」は本 ADR の 1 で置き換える(操作する面は、別プロジェクトの中央アプリとして作る)。「深掘りは既存エージェント内」のうち続きの対話は、デスクのエージェントのセッションに加えて、signal-forge 自身が答える経路(4)を持つ。substrate(Obsidian)・安全条件・英語コンテンツの訳と解説の要件は変えない。

## なぜ / トレードオフ

- **却下: Telegram だけで完結させる**(ノートの本文も Telegram に送る)。→ 解説ノート(平均 3,500 字)は収まるが、対訳(平均 11,000 字・最大 5 万字)はチャットでは読みにくく、過去ノートの横断閲覧もできない。他のサービスも束ねたいという要望にも応えない。
- **却下: Obsidian のスマホアプリを読む面にする。** → vault の同期の運用が要り、操作(質問・take)と読む面が分かれたまま。
- **却下: Claude のスマホアプリを読む面にする。** → Claude がノートを読む経路(外から届く MCP サーバか、Notion への写し)が要り、受信ポートや外部への書き込みの安全条件を見直すわりに、サービスを束ねる操作面にはならない。
- **却下: signal-forge の中に専用アプリを作る。** → 束ねたいのは複数のサービスで、signal-forge に入れるとサービス間の境界が崩れる。
- **採用の利点**: 実データで欠けている「質問への返事」を、アプリを待たずに埋められる。答えを作る部分は中央アプリへ持ち越せるので、Telegram の部分を捨てても損が小さい。中央アプリは複数サービスの視点で設計できる。
- **代償(明示)**: スマホでノート全体を読む手段は、中央アプリができるまで無い(カードと質問への返事で補う)。中央アプリは新しいプロジェクトで、作るものと保守するものが 1 つ増える。

## 安全条件

- 質問への返事(GH#126)は、PROPOSAL §フェーズ2境界の調査エージェント安全条件を継承する。untrusted な本文(記事・ノート)と質問を材料に、ツールを持たせない隔離した `codex exec`(analyze・調査段と同じ隔離レール)で答えを作り、送信は orchestrator(Python)が owner chat にだけ行う。接続は long polling のまま受信ポートを開けない。
- 中央アプリの届け方(スマホから Mac のデータへの経路)は、受信ポートの方針に関わる。決めるのは中央アプリのプロジェクトで、本 ADR は signal-forge の安全条件(受信ポートを開けない)を変えない。signal-forge の口を中央アプリへ出すときに、改めて ADR で決める。
- 壁打ちで出た中央アプリの候補(Tailscale と Mac 上の中継サーバ・各サービスの MCP を束ねる・Web アプリかネイティブか)は参考であり、本 ADR の決定ではない。
