## 3. 進行ルール

- **Issue 先行**: コード作業を始める前に必ず GitHub Issue を作る(本バックログを転記)。設計変更が要る場合も Issue 化してから設計文書を更新する。
- **小 PR 分割**: 1 Issue = 1 PR。目安は 1 CLI サブコマンド or 1 コネクタ(設計 05 §9)。大きくなりそうなら Issue を割ってから着手。ローカルで一気に作り込まない。
- **相互レビュー(author ≠ reviewer)**: Claude が実装 → Codex がレビュー。commit 末尾に `Co-Authored-By: Claude ...` トレーラを必ず付け、PR の commit trailers を routing の正本とする。レビューは PR 上に 🔴 must / 🟡 should / ⚪ nit の3段階で残し、**must ゼロを merge 条件**とする(should/nit は author 判断)。複数 AI の commit が混在した PR は分割するか人間が裁定(fail-closed)。
- **CI 最小**: PR ごとに `uv run pytest` + `ruff check` をローカル実行。マイグレーションを含む PR は「バックアップ取得 → 適用 → doctor 通過」をレビューチェック項目に含める。
- **ドキュメント正本は Notion**: 開発運用ルールに従い、PROPOSAL・設計 00〜05 の確定版は Notion へ同期する。運用ポイント:
  - 仕様(PROPOSAL・設計)は**上書き更新**でリポジトリ → Notion に同期(節目 = 各マイルストーン完了時)。
  - ログ(Day 0 実測結果・週次レビュー・判定記録)は**時系列追記**。
  - ダッシュボード(Issue 消化状況・KPI 現在地)は**常に現在地を反映**(週次レビュー時に更新)。
  - レビューのやり取りは GitHub PR に置き、Notion に転記しない。

## 6. 検証期間(M3)の週次レビューの型

毎週末に実施し、結果を Notion にログ追記+ダッシュボード更新する。所要30分目安。

### 見る数値(#24 のクエリで機械的に出す)

1. **日次 KPI 達成日数 / 有効測定日数**(👍∨🔖 ≥3 の日数。合格ライン: 有効測定日の70%以上)
2. **無効日数と fail-closed 判定**(反応率≤30% の日。週3日以上なら当週 KPI は未達扱い)
3. **巡回代替日数**(夜アンケート質問1「いいえ」の日数。未回答は代替できなかった日として fail-closed)
4. **読了時間の分布**(質問2。10〜15分仮説との乖離)
5. **ソース別・カテゴリ別 👍∨🔖 率**(ピボット判定の入力)
6. **コスト着地見込み**(doctor --cost。$30 比)
7. **👍校正スポットチェック**(1週間前の 👍 から2〜3件を再評価し乖離率を記録)

### 判定

- 上記 1〜3 を PROPOSAL §撤退・ピボット条件のマトリクスに照らし、現在の位置(継続ペース / ピボット検討域 / 撤退域)を明記する。
- 乖離率(7)が高い週は選別 KPI を割り引いて解釈する。
- 無効日3日連続が発生していたら配信5件削減(`digest.max_items` = 5)を発動済みか確認。

### 次アクション(毎週必ず1つ以上)

- 関心プロファイル更新: signals の 👍🔖/👎/✅ 実例から各カテゴリ5件上限で実例節へ追記・入替(乖離実例を優先)。
- ソース棚卸し: 死亡疑いフィード(consecutive_failures ≥7)の整理、👍∨🔖 率の低いソースの enabled 見直し。
- config チューニング: ランキング係数・min_score・daily_read_cap の調整(コード変更なしの範囲)。
- 逸脱があれば: リスク台帳(§5)の該当行のアクションを起動。

### 最終判定(有効測定日14日経過直後の週末)

- 判定マトリクス(継続 = 週4日以上代替かつ KPI 合格 / ピボット = 中間域・偏在あり(再検証は1回まで)/ 撤退 = 週2日以下かつ改善傾向なし)で結論を出し、判断根拠・学び・次フェーズ(フェーズ2境界: 🔖累計8件+50%深掘り実施)への進出可否を Notion にログとして残す。
