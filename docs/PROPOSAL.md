> 本書が企画の単独で読める**正本**。`plans/` 配下(00-comparison v3・plan-a/b/c・レビューログ)は比較検討の記録であり、本書と齟齬がある場合は本書が優先する。

## 一行コンセプト

X・RSS・手動URLを毎朝10件以内の日本語ダイジェストに圧縮し、Telegram で受け取り Obsidian に蓄積する、フルスクラッチだが徹底的に最小の個人インテリジェンス基盤(A-lite)。

## 背景と解く痛み

情報収集の巡回(約1h/日、主に X。ほか RSS・ニュースサイト)に時間を費やし、「後で読む」の未読負債が積み上がっている。解く痛みは **巡回時間の圧縮** と **未読負債の解消** の2点。見逃し防止は非目標(拾えなかった情報は諦める)。

既製品調査(2026-07-05)の結論: X 取り込み+自由文の関心基準ランキング+意味論的ネガティブフィルタ+透明なフィードバックループ+Obsidian グルーを連結した製品は存在しないため、この核だけを自作する。RSS 取得・要約・UI は既存部品(feedparser、LLM、Telegram/Obsidian)に寄せ、再発明しない。

## 成功条件と KPI 測定定義

### 成功条件

全ソース稼働の運用開始から有効測定日14日の検証で、情報収集目的の巡回をダイジェスト(10〜15分)で代替できる日が**週の過半(暦日7日中4日以上)**。

### 反応ボタン(4種)

- **👍 価値あり / 🔖 深掘りしたい / ✅ 既知 / 👎 不要**
- 「読む価値あり」= **👍 または 🔖**。✅既知は価値0だが「分類は成功」として別カウント。

### 選別 KPI と合格判定(日数ベース)

- 日次 KPI: 配信最大10件のうち 👍∨🔖 が **3件以上**。
- **合格判定: 有効測定日のうち70%以上の日で日次 KPI を達成したら選別 KPI 合格。平均値では判定しない。**

### 測定無効日ルール(反応率)

- **反応率 = いずれかのボタン反応が付いたアイテム数 ÷ 配信アイテム数**。
- 反応率が **30%以下(= 無反応が70%以上)** の日は選別 KPI の**測定無効日**とし、有効測定日から除外する。
  ※旧文言「配信アイテムの70%以上に反応がない日は除外」の一意化。plan-b の「30%以上に反応」の補集合と整合。
- **fail-closed**: 測定無効日が週3日以上ある週は、当週の選別 KPI を「未達」として扱う(除外が合格方向にしか働かない構造を塞ぐ)。
- 無効日でも夜アンケート(巡回代替判定)は**独立に集計**し、暦日分母から外さない。
- 無効日が3日連続したら配信を5件に削減する(反応疲れの方を疑う)。

### 夜の1タップアンケート(巡回代替の正)

- 質問1: 「**今日、情報収集目的の巡回(X・RSS・ニュースサイト等)をした?**(はい/いいえ)」— 「いいえ」の日を巡回代替日とする。X だけに限定しない。
- 質問2: 「今日のダイジェスト読了時間(分)」— 10〜15分仮説の検証用。
- **未回答日は「代替できなかった日」として fail-closed でカウント**する。翌朝(12:00 JST)までの遅延回答は許容。

### ベースライン計測(pre/post 比較)

- **Day 0〜Week 1(まだ手動巡回している構築期間)に、Screen Time 等で X・情報収集ブラウジングの実時間を7日分記録**し、現状「約1h/日」の自己推定をベースライン実測に置き換える。この期間を逃すと不可逆。
- 運用期間中も同一指標を取り続け、時間圧縮(中核価値)を pre/post で比較する。

### 👍 の校正(遅延スポットチェック)

週次で、1週間前に 👍 を付けた記事から2〜3件を無作為に再提示し「実際にその後役立ったか」を再評価する。乖離率が高い週は選別 KPI を割り引いて解釈し、乖離実例は関心プロファイルの実例集の校正材料にする(作者=評価者の即時自己申告バイアス対策)。

### 集計の運用形態

**KPI 集計・無効日判定・件数削減・スポットチェック抽出はすべて手動**(SQLite へのアドホッククエリ+週次セルフレビュー)で行い、MVP では自動化しない。自動化はフェーズ2のフィードバックループ側の課題。

週次集計の必須出力: (1) 日次 KPI 達成日数 / 有効測定日数 (2) 巡回代替日数 (3) **ソース別・カテゴリ別の 👍∨🔖 率**(ピボット判定の入力)。

## スコープ

### やること

- **X 取り込み**: 公式 API 従量課金・逆時系列ホームTL。単価と取得範囲は Day 0 で実測(§Day 0 ゲート)。
- **RSS 取り込み**: 生存フィード5〜10本。
- **手動 URL 投入**: Telegram Bot に URL を送る。
- **LLM 分析**: 関心プロファイル(週次関心メモ+課題リスト+実例)を注入したランキング+意味論的ネガティブフィルタ。推論専用モード(§システム概要)。
- **関心プロファイル管理**: ファイルで管理しプロンプトに注入。実例は初期数件から開始、目標は各カテゴリ5件・計20件を運用中に反応ボタン実績から蓄積。
- **出口2層**: Telegram Bot(朝1回・仮 7:00 JST・最大10件・👍🔖✅👎)+ Obsidian Vault(蓄積層。抜粋+自作要約のみ)。本文は日本語。
- **夜の1タップアンケート**(巡回代替判定+読了時間)+ **🔖翌日夜の追い掛け1通**(「深掘りした? はい/いいえ」→ `signals` に記録。フェーズ2境界「🔖の50%以上を深掘り」の測定手段。v1.1 で MVP スコープと明記)。
- **運用**: 常時稼働 Mac mini、launchd の2プロセス構成(朝バッチ+受信デーモン)、CLI(`intel collect / analyze / digest / run / doctor`)、Python + SQLite、ローカルファースト。

### やらないこと(MVP)

- 深掘り自動調査(MVP は 🔖フラグ+翌日追い掛けの記録まで。調査エージェントはフェーズ2)
- フィードバックによるスコア自動調整(記録のみ)
- KPI 集計・除外判定・配信件数調整の自動化(すべて手動)
- signals の Obsidian への反映(SQLite 記録のみ。反映はフェーズ2)
- Web アプリ、Obsidian プラグイン、ベクトルDB/RAG、複数 SNS 対応
- 全文の無期限保存(恒久保存は自作要約+メタデータ+URL。全文キャッシュは TTL 付き、既定30日)
- 見逃し防止のための網羅性追求

## Day 0 ゲート(構築開始前・半日)

X 前提が崩れたらここで企画を止める。**実測項目と合否基準**:

1. **取得範囲・時系列性** — 合格: 逆時系列ホームTLで直近24hのフォロー投稿が時系列に取得でき、体感の欠落が1割未満。
2. **実効単価** — 課金メーター/クレジット消費の実測でホームTLの実効単価を確定する。公式 pricing(docs.x.com、確認日 2026-07-05)上、逆時系列ホームTLは owned reads $0.001/件の対象12エンドポイントに含まれず、**Posts Read $0.005/件の可能性が高い**。合格: 実効単価 × 日次取得上限 × 30日 ≦ **$20**(例: $0.005/件なら日次上限 約130件)。**ホームTLとリストが同単価なら「リストは5倍高い」前提が消えるため、厳選リスト方式を再検討**する。
3. **rate limit** — 期待値: 5 req/15min/user・max_results=100(確認日 2026-07-05)。1回の収集で500件超を取る場合はページング待ちが挟まるため、日次取得上限(コスト逆算値)とセットで設計。合格: 朝バッチ1回で日次上限分を取得完了できる。
4. **ノイズ率** — 娯楽フォロー混入率を実測。フィルタ前で過半なら追跡専用アカウント新設に切り替える。
5. **Developer Agreement 原文確認** — コンテンツの保存・表示・削除(deleted content の扱い)条項を確認し、X 由来アイテムの保持ポリシーを確定する。方針: **X 由来は本文を保持しない。恒久保存は自作要約+メタデータ+URL のみ。抜粋の扱いは条項確認後に確定。RSS 由来とはポリシーを分ける**。

**ゲート不通過時**: 企画を「RSS+手動 URL のみ」に縮小して再評価するか、X 取り込みのみサードパーティプロバイダ(規約グレー・凍結リスクは自アカウント外)を再検討する。

## システム概要

### パイプライン(2プロセス構成)

```text
■ 朝バッチ(launchd StartCalendarInterval、配信時刻前に実行)
[X API] [RSS 5-10本] [手動URL(受信デーモン経由でDB投入済み)]
     └──────┬──────┘
      collect(冪等・カーソル管理)
            ↓
      正規化・重複排除・本文抽出
      ※ extraction_status: ok / partial / failed。failed はタイトル+メタ+ソース名で
        degraded 分析に回す(黙って脱落させない)
            ↓
      analyze(LLM: 要約+関心プロファイル注入ランキング+ネガティブフィルタ)
      ※ 推論専用モード(ツール無効化)。1呼び出し10〜20件のバッチ判定が既定。
        timeout 120s・リトライ1回・スキーマ検証失敗は該当チャンクのみ再実行。
        全滅時はタイトルのみの degraded ダイジェストを配信
            ↓
      digest(スコア順に最大10件、日本語)
            ↓
   ┌────────┴────────┐
[Telegram Bot 配信]        [Obsidian Vault]
 1アイテム=1メッセージ       Items/ + Daily/
 +👍🔖✅👎ボタン            (抜粋+自作要約のみ)

■ 受信デーモン(long polling 常駐、launchd KeepAlive)
 ボタン反応・手動URL投入・夜アンケート回答を終日受信
   → signals ほか SQLite に記録(Obsidian への反応反映はフェーズ2)
```

### データモデル要約(SQLite 正本、Obsidian は DB にしない)

- `sources`: 種別(x/rss/manual)、config、カーソル、成否時刻
- `items`: URL・タイトル・著者・published_at・content_hash・status
- `documents`: 抽出本文(TTL 付きキャッシュ、既定30日。`intel run` で期限切れ自動削除)+ extraction_status / extraction_error
- `analyses`: 要約、スコア群、推薦理由、モデル・プロンプトver・入力hash・推定コスト
- `signals`: **👍/🔖/✅/👎**・夜アンケート回答・深掘り追い掛け回答、記録日時
- `digests`: 生成日、Markdown、item_ids

### Telegram 実装仕様

- **接続方式: long polling 固定**(受信ポートを開けない。webhook は外部公開が必要なため不採用)。
- **受信デーモンは朝バッチと別の常駐プロセス**(launchd KeepAlive で監視)。callback query は約10秒で失効するため、周期バッチでは構造的に応答できない。
- 配信は **1アイテム=1メッセージ+ボタン**(ヘッダ+最大10通。1メッセージ4096字制限対応)。
- callback_data は **64バイト以内**(item ID のみ格納)。callback 受信時は**即 answerCallbackQuery してから DB 書き込み**。
- **認可**: 所有者の Telegram user_id / chat_id の **allowlist** を持ち、それ以外からの message・callback_query は記録のみして破棄する(callback は from.id で検証)。第三者による URL 投入(悪意コンテンツのパイプライン注入)と KPI 汚染を遮断。
- bot token 漏洩時: BotFather で revoke → 再発行(運用手順として明記)。

### LLM 抽象層の要件

- codex exec / claude -p ヘッドレスが第一候補。API SDK へ1日で差し替え可能な抽象層を挟む。
- **推論専用モードで呼ぶことを必須要件とする**: claude -p はツールを全て disallow、codex exec は read-only サンドボックス。いずれも不可なら API SDK に倒す(「LLM に書き込み・送信権限を与えない」を宣言でなく設定で担保)。
- **環境変数の分離**: claude -p は ANTHROPIC_API_KEY が環境にあると API 課金を優先するため、launchd 実行環境から API キーを除外し無自覚課金を防ぐ。
- **クォータ**: Codex はトークン連動のクレジット消費(2026-04-02〜)、Claude の headless 利用は月次 Agent SDK クレジットを消費(2026-06-15〜)。本業のコーディング利用と同一枠を食い合い、枯渇するとパイプラインが止まるため、Week 1 に1日分バッチの消費率を実測する。

### プロンプトインジェクション対策(入力+出力)

- 入力: 外部本文は untrusted data 扱い・分析専用。埋め込まれた指示を実行しない。
- 構造化出力: フィールド allowlist+型・値域検証(スコアは数値範囲、理由は長さ上限)。
- **出力経路**: 配信・ノートに載せる URL は LLM 出力ではなく **DB 上の正規 URL のみ**を使用。Telegram 送信時は本文由来文字列をエスケープ。
- 自動実行アクションは持たせない(推論専用モードで担保)。

### macOS / launchd 運用の制約

- 朝バッチは StartCalendarInterval、受信デーモンは KeepAlive。
- **スリープ対策**: StartCalendarInterval はスリープ中スキップ→復帰時に1回まとめ実行になるため、pmset で配信前時刻の wake を設定(または常時スリープ無効)。
- 実行ユーザーに **Full Disk Access** を付与(launchd 背景ジョブからの Vault 書き込みは TCC でブロックされうる)。
- **watchdog**: 朝の digest 未生成を検知して Telegram に通知(処理失敗通知と併用)。

### 秘密情報の取り扱い

- X API キー・Telegram bot token は **macOS Keychain(security CLI 経由)または chmod 600 の .env(リポジトリ外 or .gitignore 済み)** に限定。
- `intel doctor` で設定ファイルのパーミッションと token 有効性を検査。
- 漏洩時ローテーション: X はキー再発行、Telegram は BotFather revoke → 再発行。

## コスト(月額、上限 $30)

## リスクと対策(上位5)

1. **ダイジェストが「未読の置き換え」にしかならず読まなくなる**(最大リスク)
   対策: 件数上限10を厳守、推薦理由と「自分への示唆」を必須出力。発生時: 件数を5に絞りネガティブフィルタを強化。それでも選別 KPI 未達なら撤退条件へ。
2. **X API の単価・仕様・取得範囲が前提と異なる**(単価 $0.005 シナリオを含む)
   対策: Day 0 ゲートで実測してから着工。日次取得上限のコスト逆算、doctor の超過アラート。発生時: 上限内に件数を絞る/厳選リスト方式を再検討/X 層を止めて RSS+手動 URL で継続(パイプラインはソース非依存)。
3. **サブスク枠ヘッドレスの不安定・規約変更・クォータ消費**
   毎朝100件規模のバッチは本業のコーディング利用と同一クォータを食い合い、枯渇でパイプラインが無言で止まりうる。
   対策: Week 1 に消費率実測、LLM 層の抽象化で API SDK へ1日で差し替え可能に、ANTHROPIC_API_KEY の環境分離、規約グレー判定時は API を第一候補へ繰り上げ(コスト再見積)。発生時: API 切替し上限 $30 内で件数調整。
4. **ランキング精度が出ず「読む価値あり」3件未満**
   対策: 価値基準は自由文プロンプト+関心プロファイル注入でコード変更なしに毎日チューニング可能。signals と遅延スポットチェックの乖離実例を週次で(手動)プロンプトに反映。発生時: 2週目にプロンプト集中改善スプリントを1回だけ実施。
5. **プロンプトインジェクション**(外部本文が LLM への指示として作用)
   対策: §システム概要のとおり入力(data 扱い・allowlist 検証)と出力(DB 正規 URL のみ・エスケープ)の両経路で防御、推論専用モードでツール実行を無効化。発生時: 該当ソースを隔離。

## 撤退・ピボット条件

**判定時点: 全ソース稼働の運用開始日から有効測定日14日を経過した直後の週末**(本書が判定スケジュールの正本。暦週の目安は Week 3 末)。

判定マトリクス(全域を被覆):

- **撤退**: 巡回代替が週2日以下、**かつ改善傾向なし**(改善傾向 = 直近週の代替日数が前週比 +1日以上)→ 開発停止。X API のコストだけ止め、学びをログに残す。
- **ピボット検討域**: 次のいずれか → ソース構成・価値基準を組み替えて2週間再検証(1回まで)。
  - 巡回代替が**週3日**(撤退でも継続でもない中間域)
  - 週2日以下だが改善傾向あり
  - 選別 KPI 未達だが、週次集計のソース別・カテゴリ別 👍∨🔖 率で特定ソース/カテゴリに価値が偏在している
- **継続**: 巡回代替が週4日以上(週の過半)かつ選別 KPI 合格 → フェーズ2境界の判定へ。

補助条件: 月額コストが2ヶ月連続で $30 超過 → X API を縮退、改善しなければ撤退(フェーズ2以降も適用)。

## フェーズ2境界(B: 深掘りループへの進出条件)

`plans/plan-b-full-loop.md` はフェーズ2の先行仕様(v1 記録)。**着手時の進出条件・KPI・ボタン仕様・接続方式は本節が正**。

- **進出条件(件数到達型。2週間固定のサンプル不足を回避)**: **🔖が累計8件以上、かつそのうち50%以上を実際に手動で深掘りした時点**で、まず「関連リンク収集のみ」の軽量版導入を検討する。フルの調査エージェントはその次。
- **深掘り実施の記録手段**: 🔖済みアイテムに対し翌日夜の Telegram で「深掘りした?(はい/いいえ)」の追い掛けボタンを送り、`signals` に記録する(自己申告を構造化し、測定不能を防ぐ)。
- **調査エージェントの安全条件**(フェーズ2設計の必須要件): サンドボックス実行(read-only 基本)・書き込み先を Obsidian の専用フォルダに限定・送信/投稿/購入などの自動実行アクション禁止・untrusted 本文を起点とする実行はツール制限必須。接続方式は long polling を維持し受信ポートを開けない。
- ランキング自動調整(signals のフィードバックループ自動化)と KPI 集計の自動化もフェーズ2で検討。MVP はデータモデル(signals・analyses のメタ情報)が将来の入力として使える状態だけを担保する。
