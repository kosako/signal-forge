# 企画書ドラフト — パターンC: 既製品ハイブリッド・最小自作

作成日: 2026-07-05 / ステータス: ドラフト / 対象読者: 本人

## 一行コンセプト

> 収集と本文抽出は Miniflux に丸投げし、自作は「選別パイプライン + Telegram + Obsidian グルー」だけに絞って、数日〜1週間で朝のダイジェスト運用を開始する。

## 背景と課題

情報収集の巡回(主に X)に約 1h/日を費やしており、時間圧縮と未読負債の解消が解くべき痛み。事前調査(2026-07-05)の結論として、全要件を連結した既製品はゼロ。自作が避けられない核は (a) X 取り込み (b) 自由文の関心基準ランキング (c) 意味論的ネガティブフィルタ (d) 透明なフィードバックループ (e) Obsidian グルー、の5点。逆に言えば、RSS の購読管理・巡回・重複排除・本文抽出は既存 OSS が完成域にあり、ここを書くのは車輪の再発明。パターンCはこの分業を徹底する案である。

## 成功条件と KPI

- 成功条件: 運用2週間後、情報収集目的の巡回をダイジェスト(10〜15分)で代替できる日が週の過半。
- KPI: 毎日最大10件配信、うち3件以上が「読む価値あり」(Telegram の反応ボタンで計測)。
- 価値基準: ↑今の課題に直結/ゲームチェンジャー級の動き/組織 AI 活用の実例・ROI 測定。↓細かい Tips/小粒ハイプ。

## 構成 — 何を買い、何を借り、何を書くか

**主構成: Miniflux(借りる)+ X 公式 API 小型コネクタ(書く)+ 選別パイプライン(書く)**

```text
[RSS 5〜10本] ──> Miniflux (Docker, Mac mini)        ← 借りる
                  購読管理 / 巡回 / 重複排除 / 本文抽出(オリジナル取得)
                        │ REST API (未読 entries)
[X 公式API] ──> x-connector.py (owned reads,          ← 書く(小)
                フォローグラフ逆時系列TL, カーソル冪等)
[手動URL] ──> Telegram Bot 受信 → trafilatura 抽出    ← 書く(小)
                        │
                        ▼
              選別パイプライン (Python + SQLite)       ← 書く(核)
              価値基準プロンプトでスコア+理由+ネガティブ判定
              LLM = Claude Code / Codex CLI ヘッドレス(サブスク枠)
                        │
            ┌───────────┴───────────┐
            ▼                       ▼
   Telegram Bot 朝配信          Obsidian Vault         ← 書く(グルー)
   最大10件+理由+反応ボタン      Daily/Items Markdown
   (👍価値あり/👎不要/既知)      (フロントマター+GENERATED領域)
```

- **買う**: X API Basic 相当の従量枠($5〜15/月)のみ。SaaS 課金なし。
- **借りる**: Miniflux(Go 製単一バイナリ、REST API、fetch original content 機能あり)。feedparser / trafilatura(RSS 用)/ 購読管理 UI / カーソル管理を全部書かずに済む。
- **書く**: 上記 (a)〜(e) の核だけ。SQLite は「分析結果・フィードバック・配信履歴」専用の小さな正本に縮小し、記事本体は Miniflux 側 DB に置いたまま URL ハッシュで紐付ける。

**代替の組み合わせ(次点)**
- RSSbrew: digest+カスタムプロンプト内蔵だが出力が RSS で、Telegram 反応ボタンとフィードバックループを足すには Django フォークが必要になり、結局自作量が主構成と変わらない。
- Readwise Reader + 公式 Obsidian 同期: 手動 URL と蓄積を$9.99/月で買う案。選別・digest は API 経由で結局自作、X も別途必要で、月額だけ増える。

## できないこと(A案フルスクラッチとの差分)

- 記事データの正本が Miniflux DB と自作 SQLite に分裂する。全アイテム横断の再分析・ベクトル検索・スキーマ拡張(analyses / signals の関連付け等)は A 案より不自由。
- 本文抽出の品質を Miniflux の実装に委ねる。失敗記事の個別チューニングは不可(手動 URL 経路で救済)。
- X・手動 URL は Miniflux を通らない別経路で、取り込みの一貫性(重複排除など)はパイプライン側で二重管理になる。
- Miniflux の API・スキーマ変更に追従する外部依存が増える(ただし OSS・セルフホストなのでバージョン固定で凍結可能。SaaS 依存よりリスクは軽い)。

## 実装計画(数日〜1週間)

- Day 1: Mac mini に Miniflux を Docker で立て、RSS 5〜10本を登録。X API キー取得、owned reads で TL 取得の疎通。
- Day 2: 選別パイプライン骨格(SQLite、Miniflux API 取り込み、X コネクタ、価値基準プロンプト v1、ヘッドレス LLM 呼び出し)。
- Day 3: Telegram Bot(朝配信+反応ボタン+手動 URL 受信)、launchd で朝バッチ登録。
- Day 4: Obsidian グルー(Daily Digest + Item Note、フロントマター、GENERATED 領域)。
- Day 5〜7: 実運用しながらプロンプトと閾値を調整。フィードバックを signals に記録し、プロンプトへ反映する透明ループの最小版を入れる。

## コスト見積(月額)

| 項目 | 金額 |
|---|---|
| X 公式 API(従量・owned reads) | $5〜15 |
| Miniflux / Telegram / Obsidian | $0(セルフホスト・無料) |
| LLM | $0 追加(Claude Code / Codex サブスク枠ヘッドレス) |
| 電気代等(Mac mini 既存) | 実質 $0 |
| **合計** | **$5〜15 / 上限 $30 内** |

既製品ハイブリッドといっても主構成は OSS 寄せなので、SaaS 課金は発生しない。Readwise 代替を採る場合のみ +$9.99。

## リスクと対策

- X API の料金・仕様変動: 最大の外部リスク。コネクタを疎結合にし、取得件数上限とコストログを必ず記録。上限超過時は RSS のみで運用継続できる縮退設計。
- LLM ヘッドレス実行の規約・安定性: サブスク枠の headless 利用が不安定なら API 従量(上限設定)へ切替可能に。プロンプトはファイル管理しモデル非依存に保つ。
- 未読負債の再生産(要約が増えるだけ): KPI を「読む価値あり3件以上」に固定し、2週間で未達ならネガティブフィルタと件数削減を優先(件数を増やさない)。
- Miniflux 依存: バージョン固定+DB バックアップ。取り込み層は interface を切っておき、A 案移行時に自作コネクタへ差し替え可能にする。

## A案(フルスクラッチ)へ移行する条件

以下のいずれかが顕在化したら、取り込み層を自作へ置き換える(選別パイプライン・Telegram・Obsidian グルーはそのまま資産として持ち越せる)。

1. 全アイテム横断の再分析・意味検索など、正本 DB の統一が必要な機能を実際に欲しくなった。
2. Miniflux の抽出品質・API 制約が KPI 未達の主因だと切り分けられた。
3. 情報源を SNS 複数・Webhook 受信などへ拡張し、既製品の守備範囲を明確に超えた。

逆に、2週間の運用で KPI を満たしているなら移行しない。パターンCの売りは構築の速さであり、動いているダイジェストこそが次の判断材料になる。
