# 企画書ドラフト: Signal Forge — パターンB(ループ完成形)

> 注記(2026-07-05): 本書はフェーズ2先行仕様の v1 記録として保存。フェーズ2着手時の進出条件・KPI・ボタン仕様(👍🔖✅👎の4種)・接続方式(long polling 固定、webhook 不採用)・調査エージェントの安全条件は **../PROPOSAL.md §フェーズ2境界** が優先する(本文の既読率50%基準・🔖✅👎表記・webhook 併記は v1 時点の記録)。

## 一行コンセプト

「選別 → 1タップ反応 → 深掘り自動調査 → 蓄積」のフィードバックループそのものを製品と捉え、最初から完成形まで設計・実装する個人用インテリジェンスサービス。

## 背景と課題

情報収集の巡回(主に X、約1h/日)が時間を食い、未読負債が積み上がっている。さらに深刻なのは「深掘りしたいと思ったものが後回しになって死ぬ」問題。ブックマークは墓場になっており、選別だけでは「気になったが調べなかった」損失は解消されない。パターンA(ダイジェスト配信のみ)はこの後半の痛みに触れないため、本案では深掘りの自動実行までをスコープに含める。

## 成功条件と KPI

運用2週間後、情報収集目的の巡回をダイジェスト(10〜15分)で代替できる日が週の過半。

- **選別 KPI**: 毎日最大10件配信、うち3件以上が「読む価値あり」。
- **ループ KPI(本案固有)**:
  - 🔖深掘りフラグ → 調査ノートが**実際に読まれた率 50%以上**(Obsidian のノート開封を frontmatter の `status` 更新で計測)。これが本案の生死を分ける指標。
  - ✅/👎 フィードバック率: 配信アイテムの30%以上に反応がある(反応がなければスコアリング改善ループが回らない)。
  - 深掘り依頼数: 週2件以上(ゼロならループ部分は過剰装備だった証拠)。

## スコープ

- **含む**: X API(owned reads)+ RSS 5〜10本 + Telegram Bot への手動URL投入 / LLM ランキング(価値基準注入: ↑今の課題への直結・ゲームチェンジャー級の動きのキャッチアップ・組織での AI 活用実例と ROI、↓細かい Tips・小粒新製品ハイプの意味論的ネガティブフィルタ)/ 朝7時 Telegram 配信(日本語、インラインボタン付き)/ 🔖による背景調査エージェント実行 / 調査ノートと全アイテムの Obsidian 蓄積 / ✅👎のスコアリングプロンプト反映。
- **含まない**: Web UI、ベクトルDB/RAG、複数SNS、サーバー運用(Mac mini ローカル)。

## システム概要

```
X API / RSS / Telegram手動URL
        ↓ collect(冪等・カーソル管理)
  正規化・重複排除・本文抽出
        ↓ rank(LLM: 価値基準 + フィードバック履歴を注入)
  朝7時 Telegram 配信(最大10件、🔖/✅/👎ボタン)
        ↓ webhook/polling で反応を記録
   ┌────┴────┐
   🔖深掘り          ✅既知/👎不要
   ↓                     ↓
 調査エージェント     feedback テーブル
 (codex exec /        → 次回ランキング
  claude -p headless)    プロンプトに反映
   ↓
 調査ノート → Obsidian 蓄積 + Telegram 完了通知
```

**データモデル要約**(SQLite 正本、Obsidian は出力先): `sources`(カーソル・状態)/ `items`(URL・本文ハッシュ・status)/ `analyses`(スコア・理由・プロンプトver・コスト)/ `feedback`(🔖✅👎・タイムスタンプ)/ `research_tasks`(深掘りキュー・実行状態・ノートパス・既読状態)/ `digests`。LLM 呼び出しは CLI サブスク枠(codex exec / claude -p)⇔ API を差し替え可能な抽象層を挟む。

## 実装計画(週単位)— 構築3〜4週間+

パターンA(約1週間)より明確に重い。これは前提として受け入れる。

- **Week 1**: リポジトリ・SQLite スキーマ・CLI 雛形 / RSS + 手動URL収集 / LLM 抽象層とランキング / Obsidian 出力。RSS だけで一巡させる。
- **Week 2**: X API コネクター(従量課金・レート管理)/ Telegram Bot 配信 + インラインボタン + 反応記録 / launchd 常駐化。**この週末からダイジェストの実運用を開始**(ループ未完成でも価値検証を先行)。
- **Week 3**: 深掘りエージェント(research_tasks キュー → headless 実行 → ノート生成 → 完了通知)/ フィードバックのプロンプト注入。
- **Week 4**: 運用しながら調整・エラー処理・`doctor` コマンド。バッファ週。深掘りのプロンプト調整はここで終わらない可能性が高い(継続チューニング前提)。

## コスト見積(月、上限 $30)

- X API owned reads: $5〜15
- LLM: ランキング・要約はサブスク枠ヘッドレスで $0。深掘りもサブスク枠内が第一候補。API フォールバック時の予備 $5〜10
- Telegram Bot / RSS: $0、Mac mini 電気代: 誤差
- **合計見込み $10〜25**。ただし深掘りを API に切り替えた場合は1件あたりのコストが読みにくく、上限超過リスクが最も高い箇所。件数キャップ(下記)で制御する。

## リスクと対策(上位5つ)

1. **未読負債が「調査レポート負債」に化ける**(最大リスク)。読まないブックマークが読まない詳細レポートに変わるだけなら、コストをかけて負債を豪華にしただけ。対策: 深掘りは **1日2件まで**(キュー超過分は翌日繰越し、繰越しが溜まったら古い順に自動失効)/ 調査ノートは**冒頭3行サマリ必須**(3行で足りるなら本文を読まなくてよい設計)/ **2週間読まれなければ自動アーカイブ**し、アーカイブ率を月次で確認。50%を超えたら深掘り機能を疑う。
2. **構築が長引き価値検証が遅れる**。3〜4週間は見積りであり超過しがち。対策: Week 2 末からダイジェスト単体で運用開始し、パターンA相当の価値を先に確定させる。深掘りが遅延してもダイジェストは動いている状態を保つ。
3. **深掘りレポートの品質不足**(浅い・的外れで読む価値がない)。対策: 調査プロンプトに「元アイテムの何が気になったか」の文脈を渡す / 最初の10件は手動で品質確認し、プロンプトをバージョン管理して改善。品質が出なければ深掘りを「関連リンク収集のみ」に格下げする。
4. **ランキング精度が出ず「読む価値あり3件」を割る**。対策: 価値基準プロンプトのバージョン管理と週次レビュー / ✅👎の実例を few-shot としてプロンプトに還流 / 2週間改善しなければソース構成(X のフォロー整理、RSS 入替)側を疑う。
5. **X API のコスト・仕様変動**。対策: 取得件数の日次上限とコストの日次記録 / `doctor` で当月累計を可視化 / 超過時は RSS + 手動URL のみに自動縮退できる設計。

## 撤退・ピボット条件

- **運用4週間後**(構築完了から2週間)に「巡回代替が週の過半」を満たさない → ソース・プロンプト調整で2週間延長し、それでもダメなら撤退(手動巡回に戻す)。
- 深掘りノートの既読率が50%未満、または自動アーカイブ率が50%超が1ヶ月続く → **ループ部分を落としてパターンA(ダイジェストのみ)へピボット**。選別に価値があれば深掘りだけ捨てればよい。
- 月額コストが2ヶ月連続で $30 超過 → X API を縮退、改善しなければ撤退。
- 逆方向のピボット: 深掘りの利用率・既読率が高い場合のみ、件数上限の引き上げや調査深度の強化を検討する(先行投資はしない)。
