## 🔴 must

1. **X API 前提が未確認のまま企画の土台になっている**(00-comparison 共通前提・未決事項、plan-a スコープ)
   ホーム TL 取得・owned reads 料金・rate limit・最低課金が崩れると A/B/C すべて壊れる。
   → 対応: Day 0 ゲート(少量取得テストで取得範囲・時系列性・費用・ノイズ率を実測)に格上げ。**反映済み**

2. **「C の部品は A へ持ち越せる、失うものがほぼない」は過小評価**(00-comparison 推奨、plan-c できないこと)
   正本 DB 分裂・重複排除の二重管理・Miniflux 依存は移行コストそのもの。統一 ID / canonical URL hash / export 設計までやるなら A 直行の方が安い可能性。
   → 対応: 推奨を A-lite 直行に変更。**反映済み**

3. **KPI が測定可能な形に落ちていない**(00-comparison KPI、plan-a 成功条件)
   「読む価値あり」がどのボタンか曖昧、案間でボタン表記が不統一、「巡回代替日」は自己申告で自己欺瞞しやすい。
   → 対応: ボタン4種(👍🔖✅👎)に確定、価値あり = 👍∨🔖、✅は分類成功の別カウント、夜の1タップアンケートを正とする。**反映済み**

4. **「今の課題に直結」「既知との差分」を判定する入力が未設計**(plan-a LLM分析、plan-c 価値基準)
   現在の課題・既知情報・優先順位をどこから与えるか未定義で、ランキングが汎用ニュース要約に退化する。
   → 対応: 関心プロファイル(週次関心メモ + 課題リスト + 実例20件)を MVP スコープに追加。**反映済み**

## 🟡 should

5. **C が A より速い根拠が薄い**(00-comparison 横断比較、plan-c 実装計画)
   Miniflux が削るのは RSS 周りのみ。クリティカルパスで比較すべき。
   → 対応: A-lite 直行の根拠として採用。**反映済み**

6. **C に本文保持 TTL・バックアップ範囲の記載がない**(plan-c 構成)
   → 対応: C は不採用としたが、TTL と「Obsidian には抜粋+自作要約のみ」を Day 0 チェックリスト #8 として明記。**反映済み**

7. **A/C に「反応しなくなる」リスクの明示がない**(plan-a 測定、plan-c リスク)
   反応率が落ちると KPI もプロンプト改善も成立しない。
   → 対応: 最低反応率ルール(70%未満の日は測定無効、3日連続で配信5件に削減)を KPI 定義に追加。**反映済み**

8. **2週間で詰まる現実的な穴は入力ソースと評価例の未確定**(00-comparison 未決事項)
   → 対応: Day 0 チェックリストの「ユーザーが決める」5項目として明記。**反映済み**

9. **B のフェーズ2進出条件が緩い**(plan-b ループKPI)
   既読率50%は開いた/読んだの区別が弱い。
   → 対応: 進出条件を厳格化(🔖週2件以上 + 手動深掘りが実際に読まれている場合のみ、まず関連リンク収集のみから)。**反映済み**
