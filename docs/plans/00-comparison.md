## 3. 推奨(v2: Codex レビューを受けて変更)

**推奨: A-lite(= プラン A のスコープを1〜1.5週間分に絞った最小フルスクラッチ)に直行する。C は採用しない。B はフェーズ2の仕様書として保管する。**

v1 では「C で始めて A に育てる」を推奨したが、Codex レビューの次の2指摘を妥当と判断して撤回した:

- **「C の部品は A に持ち越せるので損がない」は過小評価**。C 自身が正本 DB の分裂・重複排除の二重管理・Miniflux API 依存を認めており、これは移行コストそのもの。統一 ID・canonical URL hash・export 設計まで最初からやるなら A 直行の方が安い。
- **「C が速い」の根拠が薄い**。C でも X コネクタ・Telegram・LLM 層・Obsidian グルー・launchd は全部書く。Miniflux が削るのは RSS 周りだけで、RSS 5〜10本なら feedparser + trafilatura で1日の仕事。クリティカルパスは RSS ではない。

### A-lite の定義(plan-a との差分)

- 構築目標を2週間→**1〜1.5週間**に圧縮。削るのは機能ではなく余白: Week 1 で RSS→分析→Telegram/Obsidian の一気通貫、Week 2 前半で X コネクタと launchd 化まで
- **Day 0 ゲート(構築開始前・半日)**: X API の owned reads を実アカウントで少量取得テストし、(1) 逆時系列 TL の取得範囲と時系列性 (2) 実効単価と最低チャージ (3) rate limit (4) 娯楽フォロー混入によるノイズ率、を実測してから着工する。X 前提が崩れた場合はここで企画を止められる(A/B/C すべて X が土台のため)
- **関心プロファイルを MVP スコープに含める**: 週次更新の関心メモ + 現在の課題リスト + 「価値あり/不要/既知」の実例(目標20件、初期は壁打ちで出た数件から開始)をファイルで管理し、ランキングプロンプトに注入する。これが無いと「今の課題に直結」の判定が汎用ニュース要約に退化する(Codex 🔴4)

### KPI の測定定義(Codex 🔴3 対応)

- ボタンは4種に確定: **👍価値あり / 🔖深掘り / ✅既知 / 👎不要**
- 「読む価値あり」= **👍 または 🔖**。✅既知は価値0だが「分類は成功」として別カウント
- **反応率が下がったら測定無効**: いずれかのボタン反応が付いたアイテムの割合(反応率=反応済み÷配信数)が **30%以下(=無反応が70%以上)** の日は選別 KPI の測定無効日(v3 で文言を一意化。fail-closed 規則含む完全な定義は ../PROPOSAL.md)。3日続いたら配信を5件に削減(反応疲れの方を疑う)
- 「巡回代替日」の自己欺瞞対策: 夜に Telegram で1タップアンケート「今日、情報収集目的で X を開いた?(はい/いいえ)」を送り、これを正とする

### B(深掘りループ)への進出条件(Codex 🟡9 対応、v1 より厳格化)

検証2週間で **🔖が週2件以上**、かつ**フラグしたものを実際に手動で深掘りして読んでいる**場合のみ、まず「関連リンク収集のみ」の軽量版から導入。フルの調査エージェントはその次。

### 推奨ロードマップ

```text
Day 0       : X API 少量取得テスト(半日ゲート)+ 初期ソース・実例の確定
Week 1      : A-lite 構築(RSS 一気通貫 → X → Telegram → launchd)
Week 2-3    : 運用検証。KPI 計測(👍🔖 3件以上/日、夜アンケートで巡回代替日数)
Week 3 末   : 継続/ピボット/撤退判定(基準・時期の正本は ../PROPOSAL.md。plan-a の「Week 4 末」は v1 記録)
検証通過後  : 進出条件を満たせば B の軽量版(関連リンク収集)から段階導入
```

### この推奨を退ける条件

- 深掘り後回し問題こそが最大の痛みだと再判定する → B を選ぶ(その場合、決定ログ #7 を明示的に覆すこと)
- Day 0 ゲートで X API 前提が崩れた → 企画を「RSS + 手動 URL のみ」に縮小して再評価するか、X 取り込みだけサードパーティプロバイダ(規約グレー・凍結リスクは自アカウント外)を再検討する

## 4. 実装前の確定事項(Day 0 チェックリスト)

**ユーザーが決める(実装で詰まる順)**:

1. 初期 RSS リスト(生き残り5〜10本の具体名)
2. X は本アカウントの逆時系列 TL か、追跡専用アカウントを新設するか(Day 0 テストのノイズ率実測で判断)
3. 「価値あり / 不要 / 既知」の実例 — Day 0 通過要件は壁打ちで出た数件のみ。「各カテゴリ5件・計20件」は運用中に反応ボタン実績から蓄積する目標値(着工ゲートにしない。v3 修正)
4. Obsidian Vault のパスと出力フォルダ名
5. 朝配信時刻の最終確定(仮: 7:00 JST)

**実装側で検証する**:

6. X API: owned reads 対象エンドポイントの公式原文・最低チャージ・rate limit(Day 0 テストで実測)
7. codex exec / claude -p ヘッドレス実行の構造化出力の安定性(Week 1 の最初に検証、不安定なら API へ)
8. 本文キャッシュの保持期限(TTL)と、Obsidian には抜粋+自作要約のみ置く方針の実装(Codex 🟡6。plan-a §スコープの方針を踏襲)
